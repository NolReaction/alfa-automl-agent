# Протокол сравнения новой политики поиска

База: `390829239bfb245e70d866c02d4cd69d51d4c0d9`. Контроль находится в отдельном detached worktree. Кандидат реализует явную опцию `search_policy="adaptive_v1"`; прежний default `legacy` сохраняется до проверки допуска.

## Гипотезы

1. Ранняя проверка разных модельных семейств полезнее двух подряд вариантов одного семейства при ограниченном времени.
2. Для MAE следует рано проверить существующие MAE objectives на внутреннем fit; обычные MSE-рецепты остаются контролем. Преобразование target предлагается только по существующему fit-only критерию и оценивается на исходной шкале.
3. Host timing позволяет выделять выполнимый timeout очередной попытке вместо деления остатка на все гипотетические refinement slots. Эвристика стоимости не является измерением сложности и не заменяет строгий deadline.

Модели, зависимости, метрики и признаки сохраняются существующими. Macro F1 decision rules не подключаются. Никаких условий по имени датасета, пути, публичной колонке, seed или audit answers.

## Development

До первого обучения фиксируются существующие девять families `benchmark_cases.ALL_CASE_NAMES`, seeds 42 и 73, budget 90 секунд на отдельный solver run, sequential baseline/candidate pairs. Получается 18 пар, 36 запусков, максимум 3240 секунд лимитов дочерних процессов плюс ограниченная подготовка и аудит стенда.

Порядок baseline/candidate чередуется между парами. Разбиения и входные bytes одинаковы внутри пары. Источники каждого solver фиксируются до серии и проверяются после каждой попытки. Отчёты development допустимо использовать для диагностики. Разрешены максимум две версии общей политики; изменение должно объяснять общий механизм, а не подбирать ответы конкретного case. Все выполненные версии и failures остаются в отчёте.

## Confirmation

До первого confirmation fit реализация и manifest замораживаются заново. Наборы: `linear_regression`, `mae_signed_nonlinear`, `mae_heavy_tailed`, `imbalanced_binary`, `multiclass_duplicates`, `categorical_shift`. Seeds: 211 и 307. Budget: 180 секунд на отдельный solver run. Всего 12 пар, 24 запуска, максимум 4320 секунд лимитов процессов плюс ограниченная подготовка и аудит.

После просмотра confirmation нельзя изменять эту версию и повторно называть тот же набор независимой проверкой. При выявленном correctness bug сначала отдельное исправление, затем новый заранее объявленный confirmation. Отрицательный итог допускается.

## Допуск default

Проверяются все пары, включая ошибки и таймауты. Loss gain равен `(baseline-candidate)/max(abs(baseline),1e-12)`; для F1/Accuracy/AUC применяется абсолютная разница score. R2 в этой измерительной матрице не используется. Разнородные исходные метрики не усредняются.

Для включения нового default требуются одновременно:

- каждый candidate confirmation run завершился с независимо проверенным CSV и штатным выходом;
- отсутствие дополнительных форматных, временных и refit отказов относительно baseline;
- для каждой family медианный loss gain не ниже -0.03 либо медианная разница bounded score не ниже -0.01;
- минимум две различные family имеют практический медианный выигрыш: loss gain не менее 0.05 либо bounded score gain не менее 0.005;
- на каждом бюджете отсутствие систематического лишения seed/финализации времени;
- отдельные реальные Research v3 API-failure runs завершают inner, terminal outer и полный refit без дополнительных внешних API вызовов;
- если доступны public datasets, ограниченная nested sanity-проверка не выявляет нового нарушения контрактов или бюджета. Непроведённая проверка указывается явно.

Даже выполнение этого ограниченного правила не доказывает рост private score. При смешанном результате политика остаётся явной опцией.

## Целостность и стоимость

Inner ranking не получает outer metric seed. Дедуп учитывает реализацию, objective, transform и features; одинаковый рецепт seed не заменяет отдельную внутреннюю проверку. Выбор финалистов фиксируется до outer. Восстановление принятых checkpoint и early prior сохраняется.

Каждый процесс ограничен общим budget; retries и recovery не получают нового времени. Никаких реальных запросов к конкурсному API или платформенных отправок. Один fit за раз, 8 потоков. RSS/CPU записываются только при доступной telemetry; её отсутствие не выдаётся за измерение.

Существующие benchmark files не редактируются. Новый runner сохраняет manifests, source/input/audit hashes, argv, versions, exit codes, все predictions и повторный независимый score. Модельные артефакты и большие логи остаются в игнорируемом `data/experiments/night_quality/`. Отправленный ZIP не изменяется.
