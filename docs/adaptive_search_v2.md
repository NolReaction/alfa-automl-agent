# Ограниченный адаптивный поиск моделей

`agent/adaptive_search.py` предлагает обычные рецепты для существующего
табличного evaluator. Он не обучает модели, не читает таблицы или файлы,
не обращается к API и не получает внешние ответы. Дедлайн, допустимость
эксперимента, реальное исполнение, пересчёт метрики и публикация остаются у host.

## Интерфейс

```python
search = AdaptiveSearch(classification=False, metric_name="RMSE", seed=42, max_trials=64)
recipe = search.suggest()
if recipe is not None:
    feedback = evaluate_on_fixed_inner_split(recipe)
    search.observe(recipe, feedback)
summary = search.report()
```

На одной итерации может быть один незавершённый рецепт. Повторный `suggest()`
возвращает его отдельную копию, не расходуя ещё одну попытку. Нужно передать
результат и для пропуска, иначе следующий рецепт не появится. По умолчанию
выдаётся не более 64 рецептов, жёсткий предел настройки — 96. Ошибки и пропуски
также расходуют лимит. Внутренний перебор повторных конфигураций ограничен.

`observe` возвращает `True` для выданного рецепта. Чужой стартовый рецепт,
который этот объект не предлагал, возвращает `False`: такой результат не
обучает optimizer и не меняет счётчики отказов. Host может сохранить свой
прежний стартовый каталог отдельно. Cosmetic `id`/`label` не входят в identity;
изменение исполняемой конфигурации с известным `id` отклоняется. Результат
нельзя записать дважды или после завершения соответствующей попытки.

Для проверенного результата нужны `verified=True`, метрика с точными
`name`, `higher_is_better` и конечным числовым `value`. Если указан `scope`,
принимается только `inner_selection`. `accepted` — результат допуска host,
а не оценка качества; проверенная метрика участвует в ранжировании и при
`accepted=False`. Внешние оценки нельзя передавать в этот объект даже под
другим названием: разделение данных обеспечивает host, не строковое поле.

Непроверенная попытка с причиной `duplicate`, `insufficient_budget` или
`finalization_reserve` нейтрально пропускается. `family_blocked` также не
увеличивает счётчик ошибок, но запрещает дальнейшие предложения этого
семейства. Три последовательные реальные ошибки одного семейства отключают
его; проверенный результат сбрасывает эту серию. Произвольный текст ошибок
не сохраняется в журнале поиска.

## Поиск и уровни ресурса

Сначала предлагаются пять коротких стартов: baseline, ExtraTrees, CatBoost,
LightGBM и linear. Затем создаются отдельные **in-memory Optuna TPE studies
для каждого семейства**. Импорт Optuna происходит только при первом таком
предложении. Используется фиксированный seed; воспроизводимость требует
одинаковых версий библиотек, последовательности предложений и обратной связи.
Если Optuna отсутствует, применяется ограниченный детерминированный random
search. Ошибка optional sampler при импорте, создании study, предложении или
записи результата также переводит оставшийся поиск в этот режим. Уже измеренный
host-результат сохраняется; повторный fit ради optimizer не запускается.
Журнал содержит только тип ошибки, без произвольного текста исключения.
Зависимости не устанавливаются в ходе решения.

TPE учится только на проверенных метриках **начального уровня** своего
семейства. Сохранённые успешные короткие старты того же объекта добавляются в
его study. Более дорогие уровни никогда не подмешиваются в эту целевую функцию:
это предотвращает сравнение разных объёмов вычислений как одинаковых trials.

| Семейство | Параметр ресурса | Уровни |
| --- | --- | --- |
| Baseline, классификация | `n_estimators` | 80 → 240 → 600 |
| Baseline, регрессия | `max_iter` | 80 → 240 → 600 |
| ExtraTrees | `n_estimators` | 80 → 240 → 600 |
| CatBoost | `iterations` | 100 → 400 → 1200 |
| LightGBM | `n_estimators` | 100 → 400 → 1200 |
| Linear | без повышения ресурса | обычный поиск регуляризации |

Повышение возможно после не менее трёх проверенных результатов одного
семейства на одном уровне. На каждые три таких результата выделяется один
слот повышения; выбирается лучший ещё не повышенный вариант из верхней
трети с учётом направления метрики. Равенства разрешаются стабильным id.
Онлайн-выбор не пересматривает уже потраченные слоты после новых результатов.

Повышенный рецепт меняет только этот параметр ресурса. Все остальные
настройки, цель и обработка признаков сохраняются. **Это новый полный fit,
а не warm start.** Во всех уровнях evaluator обязан использовать одни и те же
INNER-fit и INNER-validation строки. Сэмплирования строк или удаления редких
классов этот модуль не делает. Это ограниченная схема последовательного
повышения ресурса, а не вызов готового Hyperband/SuccessiveHalvingPruner.

Помимо регуляризации и сложности моделей TPE проверяет разрешённые настройки
missing indicators, rare-category grouping и signed log. Для MAE варианты
регрессионного boosting используют поддерживаемый MAE objective. Дата/текст,
история, внешние источники и настройки потоков не угадываются и не добавляются
в рецепты.

## Журнал и границы проверки

`report()` возвращает отделённый конечный JSON: все предложенные рецепты,
исполняемые identity, семейство, источник (`warmup`, `tpe`, `fallback`,
`promotion`), уровень, ресурс, родитель повышения, host-метрику, решение допуска,
статус и причину. Wall time записывается только если host передал конечный
`elapsed_seconds`; время обучения не выдумывается из числа деревьев.

Pure tests проверяют границы, воспроизводимость, реальные Optuna ask/tell,
направление метрики, нейтральные пропуски, запрет внешнего scope, детерминированный
fallback и неизменность повышаемого рецепта кроме ресурса. Эти тесты не
обучают модели и не доказывают улучшения качества или соблюдения RAM/CPU
конкретным worker. Для допуска профиля нужны парные реальные запуски host
с одинаковым общим бюджетом и отдельная проверка полного refit.
