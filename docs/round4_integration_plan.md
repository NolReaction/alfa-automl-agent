# Раунд 4: план host-интеграции и измерения

Зафиксирован 23 октября 2026 (МСК), до новых native запусков. База и неизменный контроль: `e62fea1bb30f1b5c2fd1663ad6421bd00280f7cb`. Связанный статус: [round4_integration_status.md](round4_integration_status.md).

## Исходные наблюдения

Пять сохранённых запусков предыдущего раунда анализируются без повторного обучения. Три регрессионных отчёта завершили 64 ordinary trials с существенным остатком бюджета; увеличение только wall-clock не является доказанным усилением. Классификационные 900-секундные запуски не дошли до adaptive trials, а эксперимент раннего hook вытеснил полезные попытки и два улучшивших INNER кандидата не прошли refit-budget gate. Ранний classification hook в main не принят.

Одинаковые code/recipe hashes на разных фазах INNER/outer/full refit не являются дубликатом обучения: fit/predict различаются. Проверка сохранённых contexts не обнаружила повторного выполнения одинакового code+recipe на той же фазе. Счётчик skipped duplicate не равен числу излишних fits; кэш без выявленного повторного исполнения не добавляем.

## Одна проверяемая правка

В `BudgetPolicy.finalization_timeouts` сначала выделяются полные estimate baseline, кандидату — minimum, затем оставшееся время делится между всеми стадиями. Поэтому при суммарно достаточном резерве кандидат получает меньше собственного estimate. Воспроизведение с fake clock на budgets 3600/10500 и измерениями baseline10/candidate100 секунд (fit64/predict16): план BO20.0757/CO198.5071/BR26.4539/CR262.2892, остаток509.326 с publication buffer; прежние allocations BO38.2904/CO180.3553/BR50.4555/CR238.2247.

Исправление ограничено распределением уже оставшегося времени: если сумма floors всех pending stages помещается с publication buffer и maximum/minimum, сначала дать floors всем, затем разделить surplus. Если не помещается, сохранить прежний приоритет baseline. Не менять admission, split, метрики, поиск, модели, общий deadline или cap стадий.

Критерий механизма: при достаточном времени allocations каждой pending стадии покрывает её capped estimate; сумма не превышает remaining-buffer; completed стадии исключены; дефицитный baseline-priority путь и 1800-секундный cap сохранены. Тесты — fake clock с граничным остатком и содержательными прежними проверками.

## Native план

1. Первый контроль: полный публичный classification TRAIN (87 670 строк) и TEST (41 166 строк), auto validation, `--mode offline --research-search adaptive --search-profile legacy --time-budget 3600`; immutable e62 checkout. Все пять входных файлов и 57 runtime sources хешируются до/после; отдельный короткий output root; свежий каталог без старого CSV.
2. После ревью и фиксации source SHA той же узкой правки выполнить кандидатский arm на копии тех же входов, том же Python/окружении и бюджете. Никаких дополнительных одновременно работающих ML-процессов. Фактические split/recipe hashes сравнить, отличия не скрывать.
3. Сохранить host reports, опубликованный CSV, фактические output bytes и receipts, timing/skip reasons. Пересчитать метрики из сохранённых прогнозов и host-only answers. Проверить полный fit, nonce/context/source/recipe/output, порядок ID и неизменность входов. Успешный процесс сам по себе аудит не заменяет.
4. Все эти данные известные public development. Более ранний классификационный опыт использовал derived task: не выдавать его метрику за строгую пару новому full-native arm. Основная новая пара — e62 против исправления на одинаковых полноразмерных входах.
5. Изменение является исправлением распределения, не обещанием прироста F1. Для приёмки необходимы тест механизма, отсутствие необъяснённой регрессии опубликованного результата/надёжности и пройденный аудит. При различиях состава поиска из-за времени не приписывать всю metric delta allocator без подтверждения. При отрицательном или незавершённом native исходе явно ограничить статус; не менять другие параметры ради компенсации.

## Окружение и последующие этапы

Локально Python 3.12, pinned core/CatBoost/LightGBM, квота 8 CPU/8 GiB. AutoGluon/XGBoost локально отсутствуют; процессный inventory может находиться вне namespace, тогда RSS и cleanup — unknown. Это не квалификация конкурсных 32 GB. Никаких live API запросов в нашем направлении.

Контроль 3600 выбран из выявленного classification starvation; регрессионную пару предыдущего раунда без причины не повторяем. 10 500-секундные парные опыты на каждой задаче выполняются после получения и принятия содержательных новых кандидатов и в подходящей среде. До этого подготовить проверяемую Windows-последовательность и точный статус незакрытой квалификации, не имитировать её коротким прогоном.

Внешние ИИ-1/2/3 и Мурад работают в своих ветках. Наш следующий независимый результат — host handoff для разрешённого INNER snapshot до API budget guards. Не создавать неиспользуемый runtime-hook до согласованного интерфейса внешнего ИИ-3. Модельные реализации и defaults остаются прежними до отдельных evidence/PR.
