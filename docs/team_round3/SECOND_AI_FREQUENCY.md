## Ограниченная гипотеза v1

Для каждой выбранной **заранее объявленной категориальной колонки** посчитать на
текущем `X_fit` количество появлений категории и добавить один числовой признак
`log1p(count_fit(category))`. Для неизвестной категории — 0. Оригинальные признаки
остаются. Максимум 16 категориальных колонок и 4096 наблюдаемых категорий на
колонку; заранее опиши консервативный отказ при превышении, без target-based отбора.

Только одиночные колонки: пары, target encoding, подбор порогов и class weights
в этом исследовании не добавлять. Так можно проверить одну понятную причину
изменения качества. Используй только declared categorical features из host-схемы;
технический ID, target и числовые поля не превращать в категории по догадке.

Строки сравниваются как точные исходные значения: буквальные `NA`, `0007`, `7`,
пустая строка и настоящий пропуск не должны случайно склеиваться. Правило для
настоящего пропуска зафиксируй явно. Обработка сохраняется во всех фазах.

Словарь каждый раз строится заново только из fitting части **этого** вызова.
Запрещены глобальный словарь, fit на `X_predict`, объединение train/test и перенос
словаря из другой фазы. Числовые имена новых полей детерминированы, коллизии с
исходной схемой отклоняются. Входные таблицы/context не мутируют.

Кандидат использует замороженный baseline-рецепт нынешнего агента, добавляя только
эту трансформацию. Builder исполняемого source должен поддерживать настоящий
`fit_predict(X_fit, y_fit, X_predict, context)` и actual `BASELINE_SOURCE`, включая
baseline с components. Обновлённые feature/numeric metadata передаются базовой
модели явно; её recipe сохраняется неизменным внутри wrapper recipe.

Wrapper source, base recipe и параметры трансформации фиксируются **до outer**.
Outer/full-data refit используют тот же код и рецепт; преобразование обучается
только на fit текущей фазы. Метки, порядок probability columns и формат выходных
предсказаний сохраняются. Регрессия и классификация допустимы; без категорий —
явный skip, без лишнего fit. Это кандидат, не новое default-поведение.

## Реальный host и равный бюджет

Основное сравнение — два плеча нынешнего `run_agent_v3(..., client=None,
local_only=True)`: контроль и тот же host с одной frequency-попыткой после
подготовки/INNER-измерения baseline. После этой попытки идёт обычное ограниченное
локальное продолжение. Не заменять контроль одной fixed ExtraTrees-моделью.

Source baseline берётся из реального замороженного baseline этого запуска.
Допуск frequency идёт через штатный `_assess_candidate` и его measured cost/refit
feasibility. Нельзя вручную выставлять accepted или выбирать победителя по audit.
Экспериментальное подключение допускается внутри твоего driver без изменения
общего runtime; в отчёте точно укажи точку и способ подключения. Драйвер не должен
выключать guards, менять очередь контроля или оставлять одному плечу меньше времени.

От старта child до конечного CSV — единый wall-time cap; импорты, подготовка,
transform, обучение, локальное продолжение, outer, fallback и refit входят в него.
Финальный резерв и публикация остаются у host. Не обещать 32 GiB или измеренный
RSS, если среда/monitor этого не подтверждает.

Фиксируй совпадение baseline code/recipe hashes и локальные admissions. При
несовпадении baseline это сравнение полного агента; чистый эффект frequency
не доказан. Даже при совпадении может меняться распределение времени.

## Метод до обучения и серии

Сначала напиши протокол, заморозь исходники, configs, split IDs, seeds, варианты
и порядок плеч. Отдельные preflight и protocol smoke не являются quality evidence.
Ответы audit живут только у host за пределами task-каталога solver.

Development: четыре фиксированных синтетических случая на seed 701, включая
редкие классы/категории, категориальную задачу без ожидаемого сигнала частот,
регрессию и отсутствие категорий. Confirmation: два заранее выбранных
категориальных случая на новых seeds 1907 и 7919. Итого 8 пар/16 запусков.
По 90 секунд на плечо, общий активный coordinator cap 1800 секунд. Пару начинать
только при остатке на оба полных плеча; укороченное плечо не считать сравнимым.

Формулы генераторов и validation policies зафиксировать до результатов.
Условие положительного случая не строить из test-частот: словарь test запрещён
даже в сконструированной демонстрации. Сохранить все отказы, проигрыши и ошибки.
После development не менять метод; перед confirmation записать отдельный seal.

Дополнительно, если доступны данные публичной классификации: отдельные known
TRAIN grouped folds 0 и 1, по 300 секунд на плечо, отдельный cap 1400 секунд.
Использовать существующее разделение групп дубликатов; не получать правильные
ответы test из сети/шаблона. Публичный случай уже изучен и не является confirmation.
Данные в git не добавлять. Если CSV нет — укажи точные проверенные пути и
`skipped_missing_data`, не подменяй публичную проверку синтетикой.

Тяжёлые серии на общей машине согласовать по времени с основной работой/Мурадом;
параллельная нагрузка на одном host портит сравнение времени.

## Что проверяет независимый audit

- Реальный native startup, точный INNER split и fit-only category counts.
- Valid typed host feedback; никакого принятия по stdout/напечатанной метрике.
- Frozen source/recipe, точные nonce/receipt/output hashes.
- Настоящие outer и полный refit на ожидаемых строках.
- Опубликованный CSV и last-valid checkpoint соответствуют refit receipt.
- Audit-метрика пересчитана из CSV; Macro F1 и per-class вред сохранены.
- Baseline/control не изменены трансформацией или неудачным кандидатом.
- Re-audit читает сохранённые доказательства, не обучает и не чинит артефакты.
- Tampering/неполная пара/пропущенный refit/source or environment drift не
  превращаются в completed; проверка работает и при `python -O`.

Unit tests должны отдельно покрывать unknown/missing/literal categories, row and
batch-order invariance, отсутствие влияния predict-распределения на словарь,
разные словари inner/outer/refit, collisions, limits, mutation, probability class
order и source с реальными baseline components. Тестовый fake-worker доказывает
протокол, а не качество ML; эти результаты в quality таблицу не включать.

## Сдача и решение

Собственный PR с семью файлами, точными командами, base/executable/method SHAs,
честными результатами и ограничениями. Запускать profile tests и обычный CI
на закреплённых зависимостях. Исследовательские данные и модели — в ignored data,
в отчёте — компактные метрики/хеши/команды, без ключей и `.env`.

Внешние модельные API: 0. Платформенные отправки: 0. Defaults не менять.
Решение «не интегрировать» допускается и должно быть явным, если cost/качество
не оправдывают кандидата. Включение в общий runtime делает основной ИИ после
приёмки и измерений; не заявлять готовую production-интеграцию из стенда.
