## Зачем нужен новый модуль

Сейчас `HistoryConfig` требует явные ключ и период. Публичный пример использует
известный набор признаков здания, который нельзя зашить в универсальный агент.
Новый модуль по разрешённой части X предлагает до четырёх структурно допустимых
конфигураций для будущей INNER-проверки. Он не получает y, test, outer, пути,
метрику или API и не выбирает вес смешивания.

Название `year`, числовые значения или монотонность сами по себе не доказывают
наличие времени. Только host разрешает трактовать определённые поля как период.
Разрешённая часть ключа также не является доказанным ID объекта. При одинаковых
наблюдаемых признаках разные сущности могут выглядеть одинаково.

## Зафиксированный интерфейс v1

```python
def propose_history_schemas(
    raw_columns, *, task_type, feature_columns,
    allowed_period_columns, allowed_key_columns,
    explicit_key_sets=(), numeric_key_columns=(),
    positive_key_columns=(), limits=None,
) -> dict:
    ...
```

`raw_columns` — прямоугольный mapping `column -> sequence[str | None]`, только
из INNER-fit признаков, до preprocessing. Модуль использует стандартную
библиотеку; файлового ввода/вывода, окружения, сети, часов и моделей нет.
Хост отделяет target и технические ID до передачи `feature_columns`.
Все разрешённые/явные колонки должны быть подмножеством feature_columns и X.
Неверные типы, повторяющиеся/неизвестные имена, bool вместо лимита, некорректная
форма дают безопасный ValueError. Исходные структуры не изменяются.

Возвращай конечный JSON-совместимый dict:

```python
{
    "version": 1,
    "status": "proposed",  # также abstained / limited
    "reason": None,
    "scope": "inner_fit_features_only",
    "auto_activate": False,
    "proposals": [{
        "config": {
            "key_columns": ["entity_part"],
            "period_column": "period_feature",
            "numeric_columns": [],
            "positive_columns": [],
            "ambiguity_policy": "past_unique_only"
        },
        "evidence": {
            "rows": 0, "eligible_rows": 0,
            "strict_past_history_rows": 0,
            "past_unambiguous_history_rows": 0,
            "past_ambiguous_history_rows": 0,
            "distinct_keys": 0, "distinct_periods": 0
        },
        "identity_verified": False,
        "reason": "structurally_eligible_for_inner_measurement"
    }],
    "limits": {}
}
```

Каждый config должен проходить существующий `HistoryConfig.from_json()`.
Не возвращай predictions, принятый вес, `accepted=True` или утверждение
об улучшении. `identity_verified` всегда False: y и истинная сущность неизвестны.
Политику `past_unique_only` фиксируй заранее; сравнение с `allow` принадлежит
следующему измерению host, а не перебору на скрытых ответах.

## Ограниченный поиск и точность

Начальные пределы: 2 разрешённых периода, 12 возможных частей ключа,
24 полностью проверяемых конфигурации, 4 итоговых предложения.
Автоматические ключи: комбинации шириной до 3. Явные `explicit_key_sets`
могут включать до 6 частей и проверяются первыми, без изменения смысла имён.
Это позволяет проверить длинный ключ без полного комбинаторного перебора.
Названия публичных колонок/классов в алгоритме запрещены.

Порядок кандидатов и tie-break детерминированы, документированы и независимы
от порядка строк/колонок/словарей. Ранжируй по заранее выбранным структурным
показателям: покрытие прошлой историей, неоднозначность, сложность ключа.
Большое покрытие не должно превращаться в доказательство правильной сущности.

Периоды сравниваются точно через Decimal, без float и context-rounding.
Числовые ключи нормализуются только по explicit numeric_key_columns,
положительность требуется только для explicit positive_key_columns.
Пропуски и пустые строки не образуют общий объект; буквальные `NA` и `?`
сохраняются. Семантика должна совпадать с принятым адаптером Мурада.

Для строки периода t прошлое существует только в периодах `< t`.
Неоднозначность определяется повторами в доступном прошлом. Ответы того же
периода, будущие строки и состав query-batch не являются источником истории.
Нет разрешённого времени, только один период или нет прошлого покрытия:
явный abstained с причиной. Для classification также отказ.

Установи явный предел строк/элементов работы до дорогого расчёта. Превышение
возвращает limited с фактическими счётчиками; нельзя молча взять первые строки
и представить результат как полный. Не проверяй всё сочетание колонок вне cap.

## Эксперимент и тесты

Перед первым audit зафиксируй каталог, лимиты, ранжирование и seeds 211, 907, 4003.
Ориентир 10–12 семейств небольших таблиц:

1. Чистая панель объектов, в том числе с переименованными колонками.
2. Составной ключ, отдельные части которого сталкиваются.
3. Длинный ключ из explicit_key_sets.
4. Отсутствует разрешённый период, единственный период, уникальные объекты.
5. Константный/грубый ключ с коллизиями; технический счётчик, похожий на время.
6. Пропуски, literal labels, большие/дробные близкие периоды.
7. Повторы в прошлых периодах и перестановки строк/колонок.
8. Обманчивый случай: одинаковый наблюдаемый ключ принадлежит разным сущностям.

Настоящий ID объекта хранится только у audit fixture и никогда не передаётся
proposer. Целевых значений не передавай вообще. Для небольших таблиц сделай
независимый простой oracle подсчёта покрытия/неоднозначности, без вызова той же
функции, которую проверяешь. Отдельно проверь совместимость configs с адаптером.

Обязательные строки отчёта: попадание известной допустимой схемы в top-4,
ложные отказы на пригодных случаях, все ложные совпадения по истинным сущностям,
нарушения hard contract, покрытие и неоднозначность каждого предложения,
число проверенных схем/время/лимиты. Нельзя пройти проверку вечным пустым списком.
Для одинакового X с разной скрытой истинной идентичностью предложения должны
совпадать: покажи этот предел возможностей явно.

После заморозки кода проверь новые реализации тех же семейств с seeds 8081,
12007. После просмотра результатов не меняй ранжирование под эту серию;
новые правки требуют отдельной серии с честным статусом exploratory.
Добавь ограниченный scaling 1000/10000/100000 строк с зафиксированным cap.
Обучать модели и пересчитывать ML-метрики для этого задания не требуется.

Тесты должны ловить незаконные колонки, точность периодов, row-order dependence,
утечку того же периода, недостаток прошлого, ложное auto-activation, мутации
входов, неограниченный перебор, неверные лимиты и literal missing semantics.
Результаты в игнорируемой `data/experiments/history_schema/`, компактные таблицы
и точные команды в отчёте. Память, если недоступна, не объявляй измеренной.
