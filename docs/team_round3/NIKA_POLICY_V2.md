## Зачем это нужно

Ты взяла правильный блок: ограничение контекста Qwen, сохранение полезной обратной

## 1. Отделить завершение исследования от финального CSV — приоритет P1

Сейчас `_decide` требует `baseline.retained_output_valid` даже для закрытия
исследовательского диалога; `_next` на стадии finalize/при нехватке времени
просит модель сохранить результаты. См. текущие строки 803–815, 890–915.

В v3 порядок другой:

1. LLM пишет candidate, recipe и hypothesis.
2. Host измеряет INNER и фиксирует допустимый рецепт.
3. Диалог закрывается.
4. Host выполняет outer, полный refit, проверку и публикацию CSV.

До шага 4 у корректного запуска может ещё не быть итогового CSV. Нельзя отмечать
замороженный рецепт как `retained_output_valid=True`: это другой факт.

Добавь явную семантику завершения **research dialogue** в контракт policy,
сохранив прежнее поведение legacy-контракта. Форму нового поля опиши в отчёте.
Нужны отдельные факты о проверенном кандидате/возможности host-финализации и
о действительно сохранённом CSV. Поддержанный v3-диалог может завершиться после
требуемого host-verified LLM trial, не обещая готовый submission.

Инструкции v3 не должны поручать LLM outer, полный refit или публикацию CSV.
Остановка policy передаёт управление host; его deadline, локальное продолжение,
refit и восстановление не заменяются policy. После candidate freeze исследовательские
API/tool-вызовы не возобновляются. Нельзя увеличивать счётчик проверенных LLM-trials
за счёт анализа, baseline, локального поиска или history-кандидата.

Учти короткие бюджеты: жёсткое правило «осталось меньше 300 секунд» не должно
заставлять всякий 90–300-секундный smoke заканчивать исследование до первого
разрешённого эксперимента. Сделай порог явным параметром либо используй явный
факт доступности исследовательского времени от host. Общий резерв считает
`BudgetPolicy`; policy не рассчитывает его заново и не ослабляет guards.

## 2. Поддержать реальные формы гипотез — приоритет P1

Проверка строки в `_trial`/`compact_tool_feedback` сейчас не принимает объект
гипотезы (около строк 330, 459–464). В `build_model_messages` такой feedback
попадает в неструктурированный fallback (около 1145–1153); snapshot с такой
попыткой может быть отклонён целиком.

Важно: обычный `read_hypothesis` LLM возвращает **строку** — эта ветка совместима.
Но host-local и новый host-history передают объект вида `{"hypothesis": text}`.
Для их сводки нужен явный нормализатор, сохраняющий origin и полезный
текст, с очисткой до сокращения. Не превращай произвольный JSON в подтверждённый
факт и не переноси все вложенные поля в prompt.

Проверь фактические формы `_assess_candidate` и `inner_feedback`, включая
`verified=False`, отказ из-за `refit_budget`, отсутствие diagnostics и неподдержанную
метрику. Нельзя незаметно терять typed accepted/verified/metric из-за формы hypothesis.

## 3. Исправить идентичность повторов — приоритет P2

Сейчас `_repeats_earlier` сравнивает `code_hash`, а `recipe_hash` в Trial не
сохраняется (примерно строки 322–341, 706–713).

В v3 один и тот же `fit_predict` с разными рецептами — нормальные разные попытки:
например, глубина 3 и глубина 6. Сохраняй optional `recipe_hash` и для v3 определяй
тождественность по `(code_hash, recipe_hash)`. Разный recipe не должен становиться
`repeated_code` только из-за общего исходника или похожего текста гипотезы.
Legacy-контракт без recipe hash обрабатывай явно, без выдуманного hash.

## 4. Закрыть очистку метаданных сообщений — приоритет P2

В текущем builder очищаются content/arguments, но `tool_calls[].id`, function name
и `tool_call_id` переносятся без `redact` (около строк 1162–1174). Проверочный секрет
в этих полях сохраняется в итоговом запросе, что расходится с заявленным контрактом.

При обнаружении секрета допустим безопасный `PolicyInputError` без значения поля.
Если выбираешь преобразование ID, связь assistant/tool и уникальность ID должны
сохраняться; коллизии после redaction недопустимы. Не обрезать ID и имена инструментов
ради размера. Обычный `run_python` и нормальные provider IDs должны остаться прежними.

## 5. Измерить байты относительно нынешнего v3 — приоритет P2

Сохрани прежние результаты как **legacy replay**. Текущие −80,2% получены на
реконструкции старого SYSTEM_PROMPT и накопления ResearchLedger.context; это
не измерение экономии нынешнего Research v3.

Добавь отдельную серию для фактического `SYSTEM_V3`, его contract/feedback и
обновляемого бюджетного сообщения. В нынешнем `_request_completion` snapshot
бюджета уже добавляется к копии запроса, а не накапливается в постоянной истории.
Не добавляй старое накопление в новый контроль ради большего выигрыша.

Сравнивай одинаковые исходные транскрипты до/после policy. Размер считай для
полного messages, которое пойдёт провайдеру, включая актуальную host-сводку и
последнее бюджетное сообщение. Системный prompt и task сохраняются, права модели
и смысл host-контракта не меняются. Фиксированную добавку нового представления
контракта включай в стоимость policy: не добавляй её искусственно старому контролю
и не вычитай из нового запроса. Сравнение с одинаковым дополнительным префиксом
допустимо как отдельная абляция самого сжатия, но не как замер неизменённого
нынешнего runtime. Учитывай все шаги и случаи увеличения размера.

Минимум сценариев: большой inspection, несколько корректных trials, traceback
и исправление, multi-tool group, раннее finish, мало времени, API error,
неподдержанная метрика, неполная группа, history/local feedback.

В отчёте отдельно: bytes, реальные provider-reported tokens при их наличии,
оценочные tokens, API attempts/responses. Здесь нет запроса на реальный Qwen:
provider tokens/рубли/ML-качество остаются неизмеренными. Повтор сценария не
считается реальным исследованием ML.

## Проверки перед сдачей

На зависимостях `requirements.txt` выполни:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_research_policy -v
.\.venv\Scripts\python.exe experiment_research_policy.py --label v3-compat
.\.venv\Scripts\python.exe dev_check.py
```

Обязательные содержательные тесты:

- реальный импорт `SYSTEM_V3` и fixtures manifest/feedback актуального v3;
- research completion с frozen+INNER receipt, но без итогового CSV;
- отсутствие выполненного trial и анализ вместо trial не дают ложного complete;
- host finalization не становится поручением LLM;
- одинаковый code + разный recipe не объявляются повтором;
- строковая LLM hypothesis и объектная local/history hypothesis сохраняют
  структурированные host-факты, но имеют раздельные счётчики;
- изменение outer/test sentinel не меняет research messages/decisions в mock
  host-проекции; outer поля не передаются policy, их происхождение не угадывается;
- tool ID/name с секретом безопасно отклоняется либо согласованно преобразуется;
- неполные группы не дополняются фиктивными результатами;
- невозможность вместить SYSTEM_V3+контракт даёт явный контролируемый отказ,
  после которого host может продолжить обычную финализацию;
- входы не мутируют, очистка предшествует сокращению, bytes измеряются точно.

Твоя часть этих проверок — чистые контракты, typed results и документированная
mock-проекция host-фактов. Настоящий freeze/API-stop, изоляцию outer и восстановление
финализации проверит основной ИИ отдельными integration tests общего runtime.

Сам модуль остаётся чистым: без чтения файлов, `.env`, часов, сети, обучения,
исполнения кода и собственного доступа к RunState. Входы и происхождение метрик
контролирует host. Mock HTTP допускается только на localhost с фиктивным ключом;
отдельно укажи число таких запросов. Внешние модельные API и новые обучающие
quality/скоростные benchmark-серии для этого ТЗ не нужны. Штатные ML fits из
регрессионных тестов `dev_check.py` допустимы; это отдельная проверка, поэтому
нельзя объявлять для всего полного test suite ноль fits без измерения.
