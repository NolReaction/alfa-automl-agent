# Конкурсный запуск

Сверено 20 октября 2026 с файлами из формы отправки (`baseline.py`,
`requirements.txt`, «Альфа Хак_AutoML.pdf») и новой
[инструкцией подключения API и загрузки решения](https://docs.google.com/document/d/17yxOkrdFHeQFX29iCz3f6noMs3l9cW2v/edit).
В ZIP включается предоставленный список зависимостей; baseline и PDF не включаются.
Эта инструкция описывает проверенные требования и реализацию; она не заменяет
оригинальный кейс.

## Интерфейс

```bash
python3 solution.py task.md
```

Без позиционного аргумента читается `task.md` из текущего каталога.
Относительные пути данных считаются от каталога Markdown. Для обеих публичных
задач итог — `submission.csv` рядом с Markdown, в порядке ID из `test.csv`.
Каждая задача запускается отдельно; результаты между задачами не передаются.

Платформа копирует в каталог задачи **только корневые `.py` и `requirements.txt`**,
затем запускает команду выше из этого каталога. Вложенные папки отбрасываются.
Поэтому сборщик преобразует пакет `agent/` в корневые `agent.py` и
`_alfa_agent__*.py`. Импорты `agent.*` работают через ограниченный список этих
реальных файлов; распаковки пакета поверх данных задачи при старте нет.
Проверки архива воспроизводят перенос только разрешённых корневых файлов.
MCP в официальном baseline — внутренняя реализация инструмента Python,
а не отдельный обязательный интерфейс запуска нашего архива.

| Режим | Поведение |
| --- | --- |
| `--mode auto` (по умолчанию) | Использует LLM, если в окружении заданы ключ и адрес API; без настроек явно включает offline fallback |
| `--mode offline` | Подбор моделей и параметров с лимитом времени, без чтения ключей и API-вызовов |
| `--mode llm` | Исследование с LLM; можно загрузить настройки из локального `.env` |

Обязательны `OPENAI_API_KEY` и `OPENAI_BASE_URL`; платформа подставляет их сама.
`OPENAI_MODEL` необязательна: локальный default — `qwen/qwen3.8-27b`, а конкурсный
прокси подставляет модель задачи. Адрес и ключ в исходниках не зашиваются.
`auto` читает только окружение процесса: `.env` разработчика не должен незаметно
переключать конкурсный запуск. Частично заполненное окружение вызывает понятную
ошибку с названиями недостающих переменных, без значений ключей.
Для локальной работы в `.env` задают адрес
`https://changellenge.up.railway.app/v1` и свой командный ключ. Системное окружение
имеет приоритет над `.env`; это одинаково работает в CLI и Alfa Lab. После изменения
настроек уже запущенное приложение нужно перезапустить. Ключ не помещают в браузерный
код, ZIP, журнал или Git.

## Что требует кейс

Страницы 5, 13–14 и 17 описывают систему под управлением LLM: анализ задачи,
генерацию и запуск кода, проверку гипотез, сравнение по своей валидации и выбор
следующего эксперимента. Обычный подбор моделей сам по себе этого
не обеспечивает. Offline fallback сохраняет полезный ответ при отсутствии API,
но не является подтверждением полного выполнения требований к агенту.

Общий API-бюджет команды на время разработки — 600 рублей в день, сброс в
03:00 МСК. Его делят все участники с этим ключом. Отдельный денежный лимит
конкурсного запуска инструкция не устанавливает.

20 октября реальный сервис ответил на короткий текстовый запрос и запрос с
вызовом инструмента: два ответа, 496 токенов суммарно по usage провайдера.
Это подтверждает доступ к модели и совместимость tool calling. Выдачу окружения
и полный запуск внутри Boosters ещё должна подтвердить следующая отправка.

Полный локальный цикл с настоящим Qwen также проверен на синтетической линейной
регрессии (100 строк train, 2 строки test), из плоского ZIP после переноса только
разрешённых корневых файлов. `OPENAI_MODEL` в окружении отсутствовала. За 207 секунд
получено 5 ответов API (68 954 токена), выполнено 6 вызовов Python-инструмента,
из них один завершил измеренный эксперимент. Управляющий код принял улучшение
RMSE с 0.693934 до 7.23e-14, проверил CSV и неизменность входов; статус —
`completed/model_finished`. Эти числа подтверждают интеграцию, а не качество
решения на реальной конкурсной задаче.

Первый короткий прогон обнаружил различие записи числовых ответов `251`/`251.0`.
Теперь регрессионные ответы сравниваются точно как конечные Decimal-значения,
а метрика считается по сохранённым исходным ответам. ID и метки классификации
по-прежнему сравниваются как точные строки. Некорректный JSON вызова инструмента
в первом прогоне не исполнялся; принятый стартовый CSV сохранился.

## Если платформа показывает только ноль

Первая отправка 20 октября 2026 получила `0`. Экран истории показывает
`18:42` и `597.0 sec` в колонке «Длительность загрузки», без кода завершения,
журнала и метрик отдельных задач. Эта длительность не подтверждает таймаут
агента. ZIP, приложенный после отправки, побайтно совпадает с проверенным
архивом коммита `bbce98c`; это исходники, а не отчёт выполнения.

Новая инструкция выявила конкретную несовместимость старой упаковки: она
содержала `agent/`, а платформа не копирует подпапки. Это возможная причина нуля;
без серверного журнала утверждать, что именно она сработала, нельзя.
Формула также допускает ноль для корректного результата
на уровне платформенного бейзлайна или хуже. Также этот экран не позволяет
исключить ошибку запуска, отсутствие CSV либо сбой API. Локально проверенный
протокол и положительная метрика holdout не доказывают прохождение платформы.

До следующей отправки:

1. Проверить извлечённый архив через настоящий SDK с локальным сервером:
   нормальный ответ, HTTP-ошибка, пустой или некорректный ответ, неверные
   аргументы инструмента. При сбое API уже проверенный CSV должен сохраниться,
   а процесс — успешно завершиться с явной отметкой fallback. Без принятого
   CSV либо при изменении исходных данных успешный статус недопустим.
2. Проверять улучшения моделей на неизменных разбиениях. Для регрессии
   сравнивать историю зданий и удаление периода на нескольких последних годах;
   для классификации — на нескольких grouped fold. В официальном списке
   доступны CatBoost 1.2.8, LightGBM 4.6.0 и XGBoost 2.1.4: сравнение другого
   семейства полезнее повторного перебора только глубины и числа деревьев.
   В расширенном подборе уже используются CatBoost и LightGBM; XGBoost в портфель пока не включён.
3. Сохранить параметры, предсказания и результаты каждого разбиения; отдельно
   проверить полное обучение и CSV на двух публичных задачах. Перед отправкой
   капитан проверяет новый PR и точный ZIP принятой версии.

Локальный имитатор и реальный Qwen проверяются отдельно: имитатор позволяет
воспроизводить ошибки, но не подтверждает доступность конкурсного сервиса.
Полезная минимальная диагностика от организаторов: команда запуска и cwd,
код завершения по каждой задаче, найден ли итоговый CSV, исходные RMSE/Macro F1
и названия выданных переменных `OPENAI_*` без значений ключей.

## Среда и ограничения

- Python 3.12; 8 CPU; 32 GB RAM; максимум 3 часа на задачу.
- Только данные задачи; без загрузки внешних данных и предобученных моделей.
- Используемые пакеты и их версии входят в официальный список. В репозитории
  `requirements.txt` — подмножество для разработки, а `requirements.platform.txt`
  — неизменённый предоставленный список. Сборщики CLI и приложения кладут второй
  файл в корень ZIP под именем `requirements.txt`. Платформа устанавливает
  зависимости сама; наше решение не вызывает `pip`.
- Внешний интернет из контейнера запрещён. В коде обучения нет сетевых загрузок.
- ZIP до **100 МБ**, даже если загрузчик пишет 128 МБ. В обновлённой инструкции:
  **3 отправки в день на команду, сброс в 00:00 МСК**. Остаток проверяется в форме.
- Подкаталоги для промежуточных результатов во время запуска разрешены,
  как и запись в `/tmp`; запрет папок относится только к загружаемому ZIP.
- Внутренний лимит исследования — 10 500 секунд, включая стартовое обучение;
  offline по умолчанию получает 600 секунд. Модели и вычислительные потоки
  ограничены восемью. Дерево процессов опрашивается каждые 50 мс; при суммарном
  RSS выше 28 GiB выполняется остановка. RSS может учитывать общие страницы
  несколько раз. Это измеряемый порог, а не жёсткая изоляция памяти ОС; при
  недоступном списке процессов отчёт явно отмечает отсутствие измерения.

## Проверка и баллы

Уточнение организаторов из чата 21 октября 2026, 00:10–00:14 МСК:
3 часа выделяются **на каждую задачу отдельно**. Запуски работают в отдельных
каталогах с собственным `task.md` и `submission.csv`; результаты между ними
не передаются. Public score — среднее двух публичных задач, private score —
среднее двух приватных; это разные оценки. Ответа о конкретных типах приватных
задач в приведённой переписке нет. Статус «на проверке» может означать очередь,
по нему нельзя заключать, что обучение идёт или решение успешно.

В том же сообщении указан endpoint проверки остатка командного ключа:
`GET https://changellenge.up.railway.app/key/info`, заголовок
`Authorization: Bearer <ключ>`. Это отдельный административный запрос, его нет
в цикле обучения. Формат ответа и денежная стоимость токена здесь не предполагаются;
оценка участника «48 ₽ за миллион» не является тарифом организаторов.

Для девяти зарегистрированных метрик новый [протокол research v3](research_v3.md)
закрепляет внешний holdout на стороне host, а исследователю предоставляет только
outer-fit и внутреннее разбиение. Старый v2 предоставлял полный train; его
исторические проверки выше не получают задним числом гарантий v3.

Qwen пишет `research_hypothesis.json`, `research_recipe.json` и
`research_candidate.py`. Host запускает функцию кандидата в отдельном процессе,
сам проверяет predictions-only CSV и считает inner selection. После завершения
диалога код/рецепт фиксируются с хешами; оба заранее фиксированных рецепта
проверяются на outer, а допущенный рецепт обучается на полном train для test.
После outer и full refit новых запросов Qwen нет. Full-data результат baseline
сохраняется до рискованного refit улучшившего кандидата. Неизменность кода,
порядка ID, входов и выходных артефактов проверяется host.

Отчёт отдельно сохраняет selection и final_check, обе внешние оценки и факт
выбора по outer. Оценка сохранённого победителя не является несмещённой
независимой оценкой выбранной системы. Обычные раздельные файлы под тем же
OS-пользователем не создают полноценную песочницу. Для неизвестной метрики
остаётся явно помеченный legacy v2 quality-unverified путь.

Public проверяет две известные задачи на скрытых целевых значениях. Локальные
RMSE/Macro F1 не являются баллами платформы. Согласно приложению 3, каждая
метрика переводится в баллы относительно результата бейзлайна платформы;
результат на уровне бейзлайна или хуже даёт ноль. Значения этого бейзлайна нам
не известны, поэтому предсказать public score из локальных метрик нельзя.

Private заново запускает решение на двух неизвестных задачах; их метрики не
раскрыты. Независимая проверка качества поддерживает CSV-контракт и девять метрик:
RMSE, MAE, MSE, R2, Macro F1, Weighted F1, Accuracy, ROC AUC, LogLoss. На иных метриках исследовательский путь требует отдельной
проверки; успешный public не доказывает универсальность решения.

Перед отправкой: `dev_check.py`, проверки приложения, сборка `build_submission.py`,
запуск извлечённого ZIP вне репозитория. Затем капитан проверяет CI и сливает PR;
архив собирается именно из принятой версии. Ключи, данные, модели, панель,
тесты и результаты экспериментов в архив не входят.
