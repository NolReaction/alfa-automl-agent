# Длинное адаптивное исследование и резервный API

Основа: main `ba1205d8ebcadd847b61eba669128db0ddc9faa1`. Изменение развивает
использование исходного бюджета задачи; оно не увеличивает лимиты платформы и
не гарантирует работу до последней секунды или рост приватного результата.

## Маршруты запуска

`python3 solution.py task.md` сохраняет общий предел 10 500 секунд. Для
поддерживаемой метрики, автоматической validation policy и бюджета больше
300 секунд по умолчанию включён `--research-search adaptive`. При наличии
API сначала работает исследовательский диалог, затем host-local поиск. Без
API тот же v3 протокол работает с `local_only=True` и нулём API-запросов.

`--research-search legacy` сохраняет прежний конечный поиск. Бюджеты не больше
300 секунд и явные random/grouped/time overrides в offline не переводятся на
новый маршрут. Неизвестные метрики также не получают новый v3-контракт.
Отсутствующая или неоднозначная метрика также не включает новый координатор:
саму задачу продолжает проверять исходный solver, без нового требования на
входе в CLI. Прямые библиотечные вызовы сохраняют `adaptive_search=False` по умолчанию —
это позволяет воспроизвести ранее зафиксированные эксперименты.

```powershell
# Полный offline бюджет, без запросов к провайдеру:
.\.venv\Scripts\python.exe solution.py data/regression/task.md --mode offline
# Прежний маршрут для сравнения:
.\.venv\Scripts\python.exe solution.py data/regression/task.md --mode offline --research-search legacy
```

## Два официальных шлюза

1. `https://api.alfahack-gateway26.ru/v1` — предпочтительный официальный адрес.
2. `https://changellenge.up.railway.app/v1` — резервный официальный адрес.

При любом из этих адресов в `OPENAI_BASE_URL` выбирается новый шлюз первым.
Если указан произвольный endpoint, он остаётся единственным: его credentials
не пересылаются на другой сервис. Домен, HTTPS, порт и путь официальных
адресов проверяются точно; похожее имя, userinfo, query или иной путь не дают
право передать ключ официальному резерву.

После typed transport/5xx/обычного overload 429 разрешена одна повторная
попытка за весь исследовательский диалог; при двух официальных маршрутах она
идёт через второй шлюз. После восстановления сохраняется работающий маршрут.
Обе попытки учитываются в прежнем лимите запросов, оценке контекста и исходном
дедлайне. SDK retries выключены, connect timeout не больше десяти секунд.
Auth/permission/shared quota exhaustion и испорченный уже полученный ответ
не вызывают переключения. Ключ и дневной бюджет двух шлюзов общие.

`--check-api` также может проверить резервный адрес после временного отказа;
это максимум два коротких запроса и отдельная явная команда пользователя.

## Использование CPU после диалога

В длинном режиме `model_finished` завершает платный диалог, но не обязательно
всё исследование. Сначала проверяются оставшиеся обычные presets, затем до
шести дополнительных host-кандидатов, затем адаптивные предложения. Всего
до 64 обычных host-local fit и отдельный cap шести extensions; до 512
рассмотренных предложений, чтобы дубликаты не создавали бесконечный цикл.
API сохраняет свой отдельный лимит по умолчанию 12 попыток и прежний token
guard. Каждая обычная попытка проходит те же INNER/outer/refit gates.

Глобальной остановки после четырёх отсутствий улучшения в этом режиме нет.
Три ошибки выполнения блокируют соответствующее семейство; нормальная
проверенная попытка без улучшения не блокирует остальные. Источники, входные
таблицы и frozen recovery baseline проверяются за пределами optional catches.

Ошибка планирования или необязательного поиска переводит локальный поиск в
`interrupted`, после чего выполняется обычная финализация. Перед продолжением
проверяются входы, исходники, неизменность baseline и все сохранённые frozen
попытки. Неуспешная проверка этой границы блокирует восстановление checkpoint;
повреждённый рецепт не становится допустимым способом получить CSV.

Адаптивный резерв использует собственные host measurements ожидающих
рецептов с коэффициентом 1,5 и масштабированием по строкам. Большой нижний
порог 30% снимается только когда все ожидающие стадии имеют измеренный рецепт;
неизвестный кандидат возвращает консервативный резерв. Абсолютный дедлайн и
cap 1800 секунд на стадию сохраняются. Это эвристическая оценка, а не гарантия
линейного времени обучения или независимый OS sandbox.

## Кандидаты

- [Адаптивный поиск](adaptive_search_v2.md): реальный Optuna TPE на базовой
  ступени и bounded продвижение перспективных настроек по числу деревьев.
  Продвижения обучаются заново, warm start не заявляется.
- [Дополнительные кандидаты](research_extensions_v2.md): fit-only частоты,
  автоматическая история для допустимой временной регрессии, CatBoost/LightGBM
  с early stopping, равный ансамбль проверенных ordinary компонентов и
  доступный AutoGluon. Неподходящий вариант получает явную причину пропуска.
- [Early stopping](boosting_candidate.md): дополнительный tuning split только
  внутри переданных fit-строк с прежней group/time policy, затем свежий fit на
  всех переданных fit-строках с выбранным числом деревьев.
- [AutoGluon 1.3.1](autogluon_candidate.md): CPU-only разрешённые семейства,
  собственный fit-only tuning, обязательный подтверждённый полный refit.
  Нет загрузки внешних весов, pip из решения, GPU, Ray или смены group/time
  проверки на случайную. Отсутствующий пакет или непригодная process metadata
  приводят к пропуску кандидата. Внутренние memory/time limits мягкие;
  исходный host контролирует жёсткий timeout дочернего процесса.

## Доказательства и пределы

`run.json` сохраняет причину остановки, остаток времени, gateway attempts,
локальные trials, feedback и измерения бюджета. Измеренное `elapsed_seconds`
обозначает wall time управляющего процесса; CPU time и недоступный RSS не
вычисляются из него. В нормальном CI AutoGluon проверяется отдельным native
workflow, стандартные Linux/Windows проверки проекта не ослаблены.

[Парный стенд](maximize_benchmark_protocol.md) сравнивает два v3 запуска на
одних задачах, с одним cap и без API. Это end-to-end сравнение новой политики,
а не изолированная оценка только TPE или одной новой фичи. Неизвестный cleanup
после отказа даёт censored и прекращает серию; успешный запуск с недоступной
полной process inventory остаётся provisional функциональным доказательством.
Само наличие этих механизмов не подтверждает рост качества или использование
всех 2:55. Ни один локальный audit не является приватным score платформы.
