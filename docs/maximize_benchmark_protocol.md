# Парная проверка длинного локального поиска v3

`benchmark_maximize.py` — отдельный стенд функциональной проверки. Он сравнивает
один и тот же v3 engine с `local_only=True` и `client=None` в двух режимах:

- `control`: `adaptive_search=False`, прежнее ограниченное локальное продолжение;
- `adaptive`: `adaptive_search=True`, новый координатор, дополнительные кандидаты
  и адаптивный подбор параметров.

Это end-to-end сравнение всей новой ветки, а не изолированная оценка одного HPO
алгоритма. По умолчанию заданы известные синтетические семейства
`nonlinear_regression` (MAE) и `multiclass_duplicates` (Macro F1, категориальные
признаки, точные метки `01`, `NA`, `class c`), seed 42, по 600 обучающих и 150
внешних строк. Эти генераторы уже использовались в разработке. Их результаты не
являются независимой confirmation или оценкой приватного скора.

## Фиксация до обучения

```powershell
.\.venv\Scripts\python.exe benchmark_maximize.py prepare --output-dir data/experiments/maximize/run-001 --time-budget 360
.\.venv\Scripts\python.exe benchmark_maximize.py run-prepared --output-dir data/experiments/maximize/run-001
```

Можно явно выбрать `--cases`, `--seeds`, `--solver-root` и `--memory-mib` на шаге
`prepare`. Бюджет должен быть строго больше 300 и не больше 10 500 секунд.
Небольшой запас сверх 300 нужен также на импорт worker: стенд отклонит запуск,
если после импорта и двухсекундного резерва не осталось больше 300 секунд для
фактического long-run режима. Рекомендуемый smoke cap — 360 секунд.

Для другого интерпретатора запускайте **весь стенд** этим интерпретатором: тогда
host, control и adaptive используют одинаковую среду. Отдельного скрытого
переключения Python между плечами нет. При наличии AutoGluon в среде новый
координатор может проверить и этот backend; при отсутствии должен сохранить
явный skip в своём журнале.

Стенд создаёт новый каталог и не перезаписывает существующий. `plan.json` и
`plan_seal.json` закрепляют до первого fit:

- точные runtime source SHA-256, Git commit и dirty-статус;
- хеши host-метода, генераторов и функций независимого аудита;
- версии окружения;
- порядок случаев, seed, метрику, общий cap и memory cap;
- две побайтно одинаковые копии входов каждого случая;
- отдельные файлы внешних ответов и их хеши.

Порядок плеч чередуется по случаям. Все плечи исполняются последовательно.
Перед и после каждого запуска повторно проверяются все sealed sources и входы.
После обнаруженного изменения дальнейшее исполнение прекращается, метрика
изменённого плеча не считается результатом исследования. Существующее плечо
или частичный `report.json` повторно не запускаются: для нового опыта нужен
новый каталог и заранее определённый план.

## Граница данных и бюджета

Worker получает только путь своей задачи, root выбранного solver, название
плеча и бюджет. API-клиент не создаётся; стандартный `run_python` удаляет API
credentials из окружения дочернего процесса. Внешние ответы остаются в соседнем
`host_audit/`, их путь и значения не входят в driver или задачу.

Это обычная граница разрешённых входов, **не OS sandbox**. Host отвечает за
внешнюю оценку только после публикации `submission.csv`. Точные строковые ID,
включая `000005` и `NA`, и классы проверяются существующим `TaskSpec`.

Оба плеча получают одинаковый внешний wall-clock cap. Driver отсчитывает его
до импортов и вычитает фактически прошедшее время плюс две секунды на запись
evidence. Этот остаток передаётся в v3 как единственный исходный бюджет; нового
бюджета после ошибки нет. Supervisor `run_python` ограничивает **весь** driver
тем же cap без дополнительного training allowance. После остановки процесса
может потребоваться cleanup; его реально прошедшее время также записывается.
Завершение за пределами cap с допуском 0.25 секунды получает явный
`deadline_exceeded`, а не успешную строку сравнения.

## Что проверяется и сохраняется

Стенд проверяет конкретный `run.json`, возвращённый текущим v3 запуском, его хеш,
версию протокола, нулевые API-счётчики, активный adaptive coordinator в нужном
плече, публикацию полного refit и цепочку outer/full-refit receipts. Финальный
CSV должен побайтно совпадать с опубликованным full-refit artifact. Сохранённые
recipe bytes дополнительно сверяются с замороженным recipe hash.

Если v3 выбросил исключение, wrapper `prepare_research` сохраняет точный
`state.run_dir` текущего запуска. Driver закрепляет существующий `run.json`
из этого каталога и его SHA-256 даже при падении: `solver_returned=false`,
`run_report_origin=observed_state_after_failure`, плюс тип исключения.
Он не ищет отчёты через glob и не выбирает другой запуск. Если исключение
случилось до наблюдения state, указатель остаётся пустым. Частичный отчёт
сохраняет stage, счётчики и наблюдения для диагностики; отсутствие refit recipe
не стирает эту диагностику. Такой отчёт не проходит контракт успешного плеча,
даже если рядом остались валидные CSV и receipts. Признак падения не доказывает
очистку процессов: при неизвестном cleanup сохраняется `censored` и серия
останавливается. Старые отчёты задним числом не дополняются.

`arm_summary.json`, общий `report.json` и `report.md` содержат:

- фактическое время driver и v3, исходный бюджет и оставшееся время;
- причины остановки диалога и локального координатора;
- число локальных, адаптивных и дополнительных попыток, семейства моделей;
- выбранное семейство/рецепт, внутренние и финальные host-оценки;
- независимо пересчитанную метрику по внешним синтетическим ответам;
- реальные execution resources и сведения о доступности process inventory;
- наблюдавшееся время подготовки и candidate inner/outer/full-refit вызовов.

Для времени фаз одинаковые наблюдательные wrappers стоят в обоих плечах.
Они не меняют аргументы, результаты или выбор моделей, а время самого
наблюдения входит в общий cap. `finalize` включает outer/refit: эти интервалы
перекрываются, их нельзя складывать как непересекающиеся части общего времени.
Число host recipe measurements также не выдаётся за число внутренних fit
AutoGluon или компонентов ансамбля. CPU time и соблюдение memory cap не
выводятся из wall time.

Все выигрыши, ничьи, ухудшения и ошибки сохраняются. Разные метрики не
усредняются: `aggregate_metric=null`. Внешние ответы не выбирают следующую
модель, seed или конфигурацию. Completion seal закрепляет JSON и Markdown.

## Отсутствующий мониторинг не маскируется

Если успешный процесс завершился, но `resources.available=false` или
`cleanup_complete=null`, CSV/receipt проверка может дать функциональный
результат. Его сравнение помечается `provisional_resource_observation`.
Если был nested timeout/ошибка памяти, ненулевой exit, ошибка запуска или
потерян execution receipt кандидата и очистка потомков не подтверждена,
плечо помечается `censored`, следующие плечи не стартуют.

Даже при полностью доступном мониторинге этот малый опыт имеет только статус
`functional_only`. Во всех строках и общем отчёте `quality_admission=false`:
автоматического разрешения включить экспериментальный метод по качеству нет.
Стенд не ослабляет правила существующих frequency/history qualification suites.

## Проверки стенда без обучения

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_maximize_benchmark -q
```

Тесты используют fake worker и фиксированные receipts. Проверяются изменение
источников/входов, сохранение cap, точные ID, отсутствие audit/API в driver,
отклонение непроверенного refit, provisional/censored resource статусы и
сохранение всех исходов. Запуск этих тестов не является native ML опытом.
