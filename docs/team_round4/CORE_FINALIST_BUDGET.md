# Наша задача: отбор доступного по бюджету финалиста v2

Дата: 21 октября 2026, МСК. Исполнители: Дима и основной ИИ.

## Конкретная проблема

В PR #27 пул хранит до шести проверенных рецептов, а shortlist содержит максимум
три модели всего: baseline, incumbent и альтернативу. Сейчас выбирается самая
сильная альтернатива, затем она отбрасывается, если её finalization уже не
помещается. Следующая более дешёвая модель не рассматривается. Это ограничение
v1 явно записано в `docs/finalist_selection.md`.

Нужное поведение: взять сильнейшую из сохранённых альтернатив, для которой
помещаются общие повторные INNER-проверки и собственный OUTER/full refit.
Если сильнейшая слишком дорогая, попробовать следующую, а не терять третью
модель автоматически. Качество не заменяется минимальной стоимостью.

## Контракт реализации

1. Пул выдаёт ограниченный детерминированный список альтернатив в порядке
   канонического host INNER-score с существующими tie-break. Метрики — detached
   copies; code/recipe identities проверяются до любого budget-отказа.
2. Baseline и текущий принятый incumbent сохраняются. Общий состав — максимум
   три distinct frozen identities, не три плюс baseline. Eviction пула не удаляет
   защищённые рецепты или их файлы.
3. Для каждой потенциальной тройки считать собственные measured timing estimates
   всех её участников, доступный cached split plan и MAX prospective finalization
   reserve. Использовать только размеры разрешённых views, без чтения OUTER y.
4. По очереди проверять альтернативы по качеству. Включать первую, для которой
   помещаются requested admissible repeats плюс finalization каждого возможного
   победителя. Не использовать тайминг incumbent вместо более дорогой альтернативы.
5. Отдельно учитывать полный резерв будущих rounds, original deadline и лимит
   1800 s на worker. Baseline recovery не считать дважды. Стоимость — оценка,
   а не гарантия; нехватка времени даёт честное сокращение/skip.
6. Если ни одна альтернатива не помещается, оставить baseline/incumbent. Если
   не помещается и их повторное сравнение, сохранить действующий безопасный
   путь finalization. Не выбрасывать incumbent ради доступности повторов.
7. Перед первым repeat фиксировать состав и копии canonical scores. Не подменять
   модель в середине раунда; при нехватке времени — partial/skip по текущему
   протоколу. Только полные shared rounds участвуют в сравнении.
8. После repeats сохранять canonical score выбранного рецепта, не среднее.
   Перед сменой победителя повторно проверять его refit feasibility.
9. Известное нарушение source/input/frozen integrity остаётся latched failure:
   последующая успешная проверка не разрешает checkpoint recovery. Дешёвый
   runner-up не является способом скрыть повреждение сильнейшего рецепта.
10. Режим по-прежнему требует явного `--finalist-selection` и 2/3 stability
    splits. Defaults, CSV/receipt contract и предел 10500 s не расширяются.

Отчёт должен показывать рассмотренные frozen identities, причины исключения,
выбранный состав, доступный остаток и состав резерва. Не объявлять результат
измеренного benchmark на основании unit tests или fake clock.

## Приёмка

Сначала целевые проверки с fake clock и реальной BudgetPolicy:

- сильнейшая альтернатива слишком дорога; следующая допустимая реально выбрана;
- дешёвая, но более слабая не обходит допустимую сильную;
- refit помещается, но вся серия repeats нет — кандидат не допущен как третий;
- более дорогой возможный победитель увеличивает защищённый финальный резерв;
- подходят только baseline/incumbent либо нет времени на дополнительные rounds;
- late budget loss, 2/3 splits, grouped/time semantics, score orientation/ties;
- повреждённый отвергнутый рецепт не маскируется budget skip или recovery;
- membership фиксирован, среднее не перезаписывает canonical metric, API=0;
- флаг выключен — старый маршрут и его настройки сохранены.

Затем небольшой native smoke с настоящими моделями и обычным host finalization:
INNER scores, выбранные hashes, полный refit, CSV и receipts. Это проверка
механики. Не обещать преимущество в качестве без отдельного сравнения.

После новых изменений — уместные integration checks, полный необходимый CI,
проверка Windows и плоского архива. Тяжёлые ML-серии на одном ПК последовательно.
До смены кода фиксировать текущий solver v1 как уже изученную версию.
