## Что уже работает и чего это не доказывает

Текущая версия умеет автономный подбор пяти семейств, поддерживает девять метрик, запускает код Qwen с контролем процессов, сверяет результат на закреплённых ответах, сохраняет лучший CSV и собирает плоский конкурсный ZIP. Числовое сравнение `251`/`251.0` в регрессии уже исправлено. Не тратить этап на повторную реализацию этих возможностей.

В полном локальном тесте Qwen был один проверенный эксперимент за 5 ответов API и 68 954 reported tokens. Однако исследовательская рабочая папка содержит полный train, включая ответы внешней проверки. В контрольном сгенерированном коде предварительная диагностика использовала все ответы, хотя финальная оценка модели считалась по `fit_rows`. Кроме того, внешняя метрика и диагностика возвращаются модели на следующих шагах.

Следствие: независимый пересчёт CSV не доказывает отсутствие подглядывания в обучении или выборе гипотез. Это основной инженерный риск этапа. Нельзя исправить его одной фразой в system prompt или тестом красивой метрики.

Отдельно проверить свежий Windows CI timeout: `app.tests.test_frontend.FrontendTests.test_auto_validation_is_exclusive_to_search_and_resolves_for_manual_comparison`, команда Node `automl_validation`, лимит 15 секунд, run `39474655516`. Предыдущая интеграция проходила Windows. При разборе тест прошёл 20/20 локальных Linux-запусков Node за 0.056–0.078 секунды; живые таймеры и сеть в harness заглушены, явный дефект не найден. Повтор только Windows job на неизменном коде запрошен. Сначала проверить его результат; при повторе сбоя измерить запуск Node и длительность сценария на Windows. Не увеличивать timeout без анализа и не отключать тест. Конкурсное ядро и Linux прошли.

## Этап 1. Измерить исходное поведение

Прочитать runner, validation, feedback, execution, текущие manifest/CSV контракты и тесты. На небольшой синтетической задаче воспроизвести путь информации: какие ответы видит исследовательский Python, что попадает в prompt, когда принимается кандидат и что происходит при следующем tool call.

Сохранить небольшой отчёт в `docs/research_v3.md`: схема данных, стадии, известные ограничения, проверяемые инварианты нового протокола. Показать тестом, что обращение к обычному исследовательскому входу сейчас позволяет увидеть outer-target. Не использовать реальный API для воспроизведения проблемы, которую видно в локальном fixture.

Зафиксировать, какие метрики используются для выбора, а какие для финальной проверки. Уже изученные публичные разбиения не объявлять новым независимым тестом. Если старый AutoML выбирает лучший вариант по outer, в отчёте это selection; менять название на «независимая оценка» без изменения процесса нельзя.

## Этап 2. Разделить исследование, проверку и финальное обучение

Сначала реализовать один сквозной сценарий регрессии на маленьких данных, затем расширить на классификацию и остальные метрики. Не пытаться одновременно переписать весь AutoML и приложение.

Целевая последовательность:

1. Host закрепляет внешний holdout и сохраняет исходные ID/ответы для своей проверки.
2. Исследователь получает только разрешённое представление outer-fit и внутреннее разбиение для гипотез. Любой preprocessing, EDA с ответами, выбор параметров и весов выполняется внутри этого представления.
3. Выбранный код/рецепт фиксируется: содержимое, параметры, версии контракта и хеш. После фиксации его нельзя незаметно заменить более удачной версией по внешней оценке.
4. Host обучает зафиксированный кандидат на outer-fit и получает predictions для outer-holdout. Правильные ответы не являются обязательным полем файла, который пишет исследователь.
5. Host проверяет контракт, пересчитывает метрику и сравнивает с корректно оценённым стартовым результатом. Внешняя оценка не возвращается в новый цикл подбора; после неё новых запросов модели нет. Невалидный либо худший кандидат оставляет прежний результат. Такой выбор между baseline и кандидатом всё ещё использует outer для приёмки: оценку сохранённого победителя нельзя объявлять несмещённой независимой оценкой. Отдельно сохраняются оценки двух заранее зафиксированных рецептов и факт выбора по outer; для независимой оценки выбранной системы нужна дополнительная неиспользованная часть или платформа.
6. Допущенный рецепт обучается на полном train для test; после доступа к полным ответам исследовательский диалог не возобновляется. CSV проходит структурную проверку и публикуется атомарно.

Продумать минимальный исполнимый контракт кандидата в `research_candidate.py`: обучение на переданном fit, прогноз на переданных features, сериализуемое описание рецепта и доказательство неизменности кода между validation/refit. Не импортировать сгенерированный модуль в основной процесс. Явные пути входов, ограничения ресурсов и выходов остаются у host. Изменения общего внешнего интерфейса сначала описать в документе, затем реализовать с совместимостью CLI.

Manifest v3 должен объявлять разрешённые входы, этап, назначение разбиений, схему выходов и порядок классов. Не зашивать target/ID/названия датасетов. Точные строки ID и меток классов сохраняются. Регрессионные ответы для host-оценки берутся из исходного snapshot. Для ROC AUC/LogLoss проверяются все необходимые вероятности и явный порядок классов.

Старые отчёты v2 остаются читаемыми; они не получают задним числом новое доказательство изоляции или статус проверки. В модели отчёта отдельно обозначить `selection`/`final_check` и происхождение оценки. Для неподдерживаемой метрики качество остаётся непроверенным, даже если CSV структурно корректен.

**Граница гарантии:** обычный Python под тем же пользователем способен обращаться к другим файлам. Раздельные представления и контракт защищают от обычного случайного подглядывания, но не создают OS-песочницу. Не использовать AST-запреты как доказательство безопасности и не обещать абсолютную изоляцию. Если полноценная OS-изоляция не реализована на нужных платформах, явно записать ограничение и проверить поведение обычного разрешённого пути работы.

## Этап 3. Подключить работу команды

Каждый модуль сначала проверяется отдельно. До появления PR коллег использовать небольшие фикстуры по контрактам; не писать за них второй конкурирующий модуль. После получения PR прочитать код и отчёт, проверить совпадение интерфейсов, затем объединить изменения в интеграционной ветке. Устранять внешние конфликты в своих файлах; изменения внутренних алгоритмов отдавать владельцу.

**Ника.** Подключить чистые `compact_tool_feedback`, `decide_next_action`, `build_model_messages` из `agent/research_policy.py`. Host передаёт versioned contract, snapshot, историю и redactor. В исследовательском snapshot v3 доступны только внутренние метрики и диагностика; внешний результат не возвращается следующей гипотезе. Полный очищенный журнал хранится отдельно; в API отправляется ограниченная проекция. Policy рекомендует действие, а host решает, разрешён ли запрос, запуск, завершение и публикация. В v3 её `complete` завершает диалог исследования и передаёт зафиксированный кандидат host; весь run ещё проходит внешнюю приёмку и refit. Условия бюджета не доверять тексту stdout или ответу модели. На несовместимом контракте выдавать понятную ошибку/fallback, не молча подставлять выдуманные поля. Точный v1 контракт — в NIKA.md.

**Таня.** Вызов `portfolio_candidates(profile, available_actions=..., limit=8)`, где profile содержит только `task_type` и `metric`. Результат имеет существующие поля `id`, `action`, `label`, `model_config`, `feature_config`. Дима определяет фактически доступные action, дедупликацию с текущим планом, общий лимит попыток и reserve на refit. Нельзя просто добавить восемь дорогих обучений сверх прежнего бюджета. Сначала включить явной опцией; default меняется только по парным результатам на равном времени.

**Мурад.** `fit_history_candidate` получает явный config, raw features, train-ответы и blend_weight; fitted adapter применяет историю к base_prediction. История работает только по прошлым периодам и явной схеме, config=None выключает её. Веса выбираются во внутренней проверке; при отсутствии истории остаётся базовый прогноз. Дима подключает fit/apply/refit и перенос диагностики. Автоматически объявлять похожие поля идентификатором здания нельзя. Точный API — в MURAD.md.

Порядок интеграции: policy → portfolio → history. У каждого подключения отдельный небольшой коммит и режим отключения. Наличие модуля в ZIP не должно само по себе менять поведение.

## Этап 4. Сделать состояние понятным в Alfa Lab

Показать компактную последовательность стадий: подготовка → внутренние эксперименты → фиксация кандидата → внешняя проверка → обучение на всех данных → результат. Текущая стадия выделена, завершённые отмечены, пропущенные объясняются кратким статусом.

Рядом с метрикой видно её назначение и разбиение. В карточке попытки — гипотеза, время, семейство/рецепт, результат принятия и краткая причина. `not_better` не выглядит как авария. При API fallback видно, что получен автономный результат, а не успешное исследование Qwen. Для истории видно включение, покрытие и причину отключения. Для бюджета показываются реальные requests/tokens и неизвестный usage; рублёвую стоимость без данных не изобретать.

Сохранить привычные запуск, остановку, журнал и выгрузку проверенного ZIP. Не добавлять терминал произвольных команд в браузер. Ключ остаётся на серверной стороне и не передаётся через отчёты, HTML или ответы API приложения. Старые результаты и импорт отчётов продолжают открываться с корректными отметками их происхождения.

## Этап 5. Проверки по рискам

Нужны проверки поведения, а не количество тестов:

- После фиксации индексов split, схемы и порядка классов изменение outer-target не меняет доступную исследователю информацию, inner-выбор и зафиксированный рецепт; оно может изменить только последующую host-оценку и решение о приёмке. До фиксации разбиения метки могут законно влиять на стратификацию. После внешней оценки нового поиска нет.
- Полное обучение возможно только после фиксации рецепта; хеш кода одинаков между validation/refit. Несвежие артефакты, изменённые входы и неправильный порядок строк отклоняются.
- Grouped/time разбиения сохраняют свои ограничения. Преобразования обучаются только на fit. Подбор веса истории не использует внешний ответ.
- Классы-строки, редкий класс, бинарные и многоклассовые вероятности, отрицательный R2, неконечные числа, неизвестная метрика/схема дают правильные статусы.
- API malformed response, quota error, неизвестный usage, exhaustion времени, timeout/OOM и падение refit сохраняют последний действительно принятый CSV. Без такого CSV ложного успешного статуса нет.
- Компактизация Ники сохраняет tool call groups, предел размера и host-факты; sensitive text очищен до включения в контекст.
- С включёнными и отключёнными расширениями работает плоский ZIP после копирования только корневых `.py` и `requirements.txt` в чистый каталог вне репозитория.

Локальные тяжёлые проверки запускать последовательно: конкуренция CPU между несколькими тестовыми процессами уже может искажать лимиты времени. Не повторять весь набор после правки одного абзаца документации. Для финального изменения кода выполнить релевантные тесты, затем штатные gates:

```powershell
.\.venv\Scripts\python.exe dev_check.py
.\.venv\Scripts\python.exe -m unittest discover -s app/tests -v
.\.venv\Scripts\python.exe app/windows/build_launcher.py --verify app/AlfaLab.exe
.\.venv\Scripts\python.exe build_submission.py
```

Linux использует `.venv/bin/python` для тех же аргументов. Проверки CI нужны на обеих ОС. Реальный API — после offline fixtures и подключения общего guard; короткий ограниченный smoke, затем при необходимости один согласованный end-to-end. Учитывать общий дневной бюджет команды; Ника не запускает параллельный независимый расход. Ключи не печатать и не коммитить.

Содержательные вехи: сначала воспроизведение риска и рабочий v3 сценарий; затем совместимость классов/метрик; затем подключение модулей; затем приложение и упаковка. После каждой вехи — проверяемый коммит. Не держать всё в одном непроверяемом гигантском diff.

Готовность означает воспроизводимый запуск, честное разделение выбора и проверки, контролируемые ресурсы, читаемые статусы и сохранность принятого результата. Она не означает гарантированный рост балла на неизвестных задачах. Финальное слияние и отправка новой версии — после просмотра капитаном конкретного PR и архива.
