## Зафиксированный интерфейс v1

Следующие имена, сигнатуры и базовые поля — договорённость для параллельной интеграции. Не переименовывай их самостоятельно. Используй стандартную библиотеку и JSON-совместимые структуры.

```python
@dataclass(frozen=True)
class PolicyLimits:
    max_messages_bytes: int = 64 * 1024
    max_tool_feedback_bytes: int = 6 * 1024
    max_recent_trials: int = 6
    max_recent_tool_groups: int = 2

@dataclass(frozen=True)
class PolicyDecision:
    stage: str
    action: str
    instruction: str
    reason: str

@dataclass(frozen=True)
class PolicyContext:
    messages: list[dict]
    diagnostics: dict

class PolicyInputError(ValueError):
    pass

class PolicyBudgetExceeded(ValueError):
    pass

def compact_tool_feedback(result: Mapping, *, limits: PolicyLimits,
                          redact: Callable[[str], str]) -> dict:
    ...

def decide_next_action(snapshot: Mapping, *, contract: Mapping) -> PolicyDecision:
    ...

def build_model_messages(*, system_prompt: str, task_text: str,
                         contract: Mapping, history: Sequence[Mapping],
                         snapshot: Mapping, limits: PolicyLimits,
                         redact: Callable[[str], str]) -> PolicyContext:
    ...
```

Функции детерминированы, не изменяют входы, не читают файлы, окружение и часы, не используют сеть и не выполняют Python. Время, права доступа, факты и очистку секретов передаёт host. `redact` — чистая функция `str -> str`; известный ключ в модуль отдельно не передаётся. Значения лимитов — положительные целые числа, кроме количества сохраняемых групп/попыток: там допустим ноль. `bool` не принимается как число.

`snapshot` версии 1 содержит обязательные ключи:

```text
version: 1
stage: inspect | research | finalize
budget: {remaining_seconds: finite nonnegative number,
         remaining_requests: nonnegative int, can_request: bool}
baseline: {status: str, retained_output_valid: bool,
           best_verified_metric: Metric | null}
last_trial: Trial | null
recent_trials: list[Trial]
counts: {verified_trials: nonnegative int, unverified_trials: nonnegative int,
         consecutive_execution_failures: nonnegative int}
finish_requested: bool
```

`Metric` — `{name: str, value: finite number, higher_is_better: bool}`. `Trial` содержит `number`, `code_hash`, `hypothesis`, `accepted`, `verified`, `metric`, `reason`, `error_kind`, `error`: номер — положительный int; hash/гипотеза/причина/ошибка — строка или null; accepted/verified — bool; metric — Metric или null. `error_kind`: null либо `execution`, `timeout`, `memory`, `evidence`, `repeated_failure`, `api`, `unknown`. Необязательные `diagnostics` и `resources` — JSON-объекты. Это нормализованный host snapshot, а не прямой импорт `RunState`; преобразование существующего ledger делает Дима.

`contract` версии 1 содержит обязательные ключи:

```text
version: 1
manifest_version: positive int
manifest_path: nonempty str
host_instructions: str
allowed_inputs: list[{path: nonempty str, purpose: str}]
required_outputs: list[{path: nonempty str, columns: list[str]}]
validation: {supported: bool, metric: Metric | null, scope: str}
completion: {required_verified_trials: positive int, allow_unverified: bool}
```

`validation.metric` описывает текущую известную host-метрику либо null; фактический лучший результат берётся из baseline. Полный manifest, массивы индексов и скрытые ответы сюда не помещаются. `host_instructions` задаёт разрешённые операции и последовательность стадий, включая refit. Дополнительные неизвестные ключи snapshot/contract игнорируй, не отражая автоматически в prompt. Новый обязательный ключ или семантику дополнительного поля сначала согласуй с Димой; текущего v1 достаточно для независимой реализации.

`history` — только переменная часть диалога из `assistant` и `tool`, без исходных system/task/contract и повторных host-сводок. Host собирает их отдельно. Assistant с несколькими tool calls и все соответствующие tool results образуют неделимую группу. Незавершённая группа, неизвестный tool_call_id, дубликат результата или структурно неверное сообщение вызывают `PolicyInputError`: host обязан закончить обработку группы до нового запроса. Не создавай фиктивные результаты для pending calls.

`PolicyDecision.stage`: `inspect`, `experiment`, `repair`, `finalize`, `finished`; `action`: `continue`, `complete`, `fallback`, `stop`. `reason` — стабильный краткий snake_case код; перечисли использованные коды в отчёте. `PolicyContext.diagnostics` содержит `version=1`, `before_bytes`, `after_bytes`, `removed_tool_groups`, `omitted_plain_messages`, `truncated_fields`, `recent_trials_included`; это размеры/счётчики, без исходных секретных текстов. `before_bytes` — очищенный несжатый кандидат того же запроса; `after_bytes` — точный итоговый размер.

Неверные типы, версии, нечисловые/бесконечные значения и некорректный protocol дают `PolicyInputError` с безопасным сообщением. Если обязательная часть не помещается, возникает `PolicyBudgetExceeded`. Не возвращай повреждённый или молча обрезанный контракт.

## Контекст и полезная обратная связь

Размер messages и feedback измеряй через `json.dumps(value, ensure_ascii=False, separators=(",", ":"), allow_nan=False).encode("utf-8")`. Лимиты относятся ко всей сериализованной структуре соответствующего результата. Это ограничение байтов, не токенов и не цены.

Сначала очисти текст, затем сокращай, затем проверяй размер. System prompt, исходная задача и обязательный host-контракт сохраняются полностью после очистки. Динамическая host-сводка одна. Удаление всей старой tool-группы допустимо; сохранение orphan tool message, обрезание JSON arguments или изменение исполненного кода ради экономии — нет. Очистка секретов в arguments должна сохранять корректную сериализацию. Если последняя группа слишком велика, её можно целиком заменить явной host-сводкой, сохранив проверенные факты, но не выдавая сводку за исходный tool result.

Приоритет имеют текущая лучшая host-метрика, причина последнего сбоя, последние гипотезы и причины отклонения. Большая первоначальная инспекция и повторяющийся успешный stdout уступают им. Сохраняй `exit_code`, timeout/OOM, безопасную ошибку, `selection.accepted`, `selection.verified`, метрику, причину и ограниченную полезную диагностику. У обрезанных stdout/stderr явно показывай факт обрезания и исходный размер. Не прячь последний traceback за большим stdout.

Применяй allowlist значимых полей; неизвестные большие поля не должны неожиданно съедать бюджет. У компактного feedback документируй оставшиеся и добавленные служебные поля. Если обязательный минимальный feedback не помещается, также используй `PolicyBudgetExceeded`.

Текст модели и stdout не могут менять host-метрику, `verified`, права доступа и бюджет. Если stdout содержит «score=1», а selection сообщает худшую метрику, сохраняется host-факт. Сводка не должна усиливать утверждение: «модель написала» не превращается в «независимо проверено».

## Адаптивная инструкция и завершение

Начальная инспекция должна читать задачу, словарь, шаблон и разрешённое представление данных, выводя краткую схему и план. Не проси печатать весь CSV, manifest, индексы или большие таблицы. При наличии baseline направляй модель к проверяемой гипотезе, а не к повторной бесконечной инспекции.

После execution error предлагай исправить конкретную причину; после timeout/OOM — уменьшить сложность. После evidence error объясняй недостающий контракт. После `not_better` сохраняй лучший результат и предлагай отличающуюся гипотезу. После улучшения фиксируй host-факт и оценивай оставшиеся ресурсы. Не считай неизменённую повторную попытку новой идеей. Используй `error_kind`; неизвестная ошибка требует нейтрального безопасного совета, а не угадывания по случайной английской фразе.

Политика совместима с текущим manifest v2 и будущим v3: не зашивай обязательность `actual`, видимость target, путь `train.csv`, имена столбцов или порядок классов. Колонки артефактов задаёт `required_outputs`. EDA разрешается только на объявленном fit-представлении или строках fit, если host явно даёт такой контракт. Не требуй full-data refit до разрешённой host стадии. Для v3 Дима передаёт в исследовательский snapshot только внутренние оценки; outer-score и диагностика внешнего holdout не должны становиться обратной связью следующей гипотезы. Policy сама не угадывает происхождение метрики: оно задаётся host-контрактом `validation.scope`. Инструкции не являются технической песочницей: код Python того же пользователя сам по себе не доказывает отсутствие доступа к другим файлам.

`complete` допустим при `finish_requested`, сохранённом валидном результате и выполненном host-контракте: при поддерживаемой метрике число verified trials не меньше `required_verified_trials`. При неподдерживаемой метрике требуется `allow_unverified` и хотя бы один unverified trial; instruction обязана обозначить непроверенное качество. Baseline, текст «готово» или напечатанная метрика сами по себе недостаточны. Улучшение метрики не обязательно: корректный `not_better` учитывается. В v3 `complete` завершает исследовательский диалог и передаёт зафиксированный кандидат host; это не статус успешного завершения всего run до внешней приёмки и refit. После внешней оценки host больше не запрашивает модель.

Когда запрос недоступен либо оставшееся время/число requests равно нулю, рекомендуй `fallback` при сохранённом результате, иначе `stop`; уже выполненный контракт завершения можно признать выполненным. Не запускай API, не устанавливай денежные лимиты и не отменяй host deadline. При слишком раннем finish и доступных ресурсах верни `continue` с конкретным недостающим действием. Финальное принятие файлов и статус run остаются у Диминого runner.
