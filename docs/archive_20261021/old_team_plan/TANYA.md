# Таня: экспериментальный портфель моделей

Ты работаешь с Таней над репозиторием https://github.com/NolReaction/alfa-automl-agent. Выполни самостоятельную исследовательскую задачу: создай небольшой поставщик модельных конфигураций, проверь новые гипотезы на реальных данных и передай результат через PR. Основной AutoML подключит интегратор после ревью. Здесь требуется полезная работа примерно на 3–6 часов: несколько содержательных итераций, измерения, анализ и проверка реализации. Не растягивай выполнение искусственно; отсутствие устойчивого улучшения тоже является полноценным результатом.

## 1. Зафиксируй исходное состояние

Базовый коммит: `ccdf49e333495d496ee3a712571199e493d790d4`. Рабочая ветка: `work/tanya-model-recipes`. Перед изменениями выполни:

```bash
git status --short
git remote -v
git fetch origin
git show --no-patch --oneline ccdf49e333495d496ee3a712571199e493d790d4
```

Проверь, что это нужный репозиторий. В чистом рабочем каталоге создай ветку от указанного SHA, а не от переместившегося `origin/main`:

```bash
git switch -c work/tanya-model-recipes ccdf49e333495d496ee3a712571199e493d790d4
git rev-parse HEAD
```

Чужие незакоммиченные изменения не трогай: не делай reset, clean, stash или checkout поверх них. При необходимости создай отдельный worktree от того же SHA. Если рабочая ветка уже существует, сначала выясни её состояние; не пересоздавай принудительно. Интернет разрешён для Git, штатной установки зависимостей и подготовки публичных данных. Вызовов модельных API должно быть **0**, API-ключ не нужен.

Прочитай `agent/models.py`, `agent/model_config.py`, `agent/features.py`, `agent/search.py`, `agent/metrics.py`, `agent/task_spec.py`, `benchmark_models.py`, `docs/expanded_validation.md`, `docs/classification_experiments.md`. Они описывают уже доступные модели, допустимые параметры и результаты, которые команда видела.

## 2. Соблюдай границы изменений

В твоём PR могут изменяться только четыре исходных файла:

1. `agent/portfolio_recipes.py` — чистый поставщик кандидатов.
2. `experiment_portfolio_recipes.py` — воспроизводимый экспериментальный runner.
3. `tests/test_portfolio_recipes.py` — проверки контракта и небольшие функциональные проверки.
4. `docs/portfolio_recipes_report.md` — компактный отчёт с измеренными результатами.

Не изменяй существующие модели, allowlist, preprocessing, search, worker, task/metric contracts, runner, UI, requirements, README и чужие файлы. Не подключай поставщика к основному AutoML. Не вводи новые зависимости, модельные семейства, target encoding, обучение ансамблевых весов или калибровку: это другой объём работы. Если существующий код ограничивает гипотезу, опиши ограничение интегратору.

Тяжёлые артефакты сохраняй в новых каталогах `data/experiments/tanya-model-recipes/<run-id>/`. `data/` уже игнорируется Git; менять `.gitignore` не требуется. Не коммить исходные данные, обученные модели и большие CSV. Не перезаписывай входы и предыдущие результаты.

## 3. Реализуй замороженный API

```python
def portfolio_candidates(
    profile: dict,
    *,
    available_actions: tuple[str, ...],
    limit: int = 8,
) -> list[dict]:
    ...
```

`profile` — словарь ровно с двумя ключами:

```python
{"task_type": "classification", "metric": "Macro F1"}
```

Разрешены `classification` и `regression`; метрику разрешай существующим `get_metric` и проверяй соответствие типу задачи. Поддерживаются RMSE, MAE, MSE, R2, Macro F1, Weighted F1, Accuracy, ROC AUC, LogLoss. Неизвестная метрика завершается явным `ValueError`, без подстановки RMSE или Macro F1. Дополнительные поля профиля запрещены. Данные, пути, результаты проверок и названия датасетов поставщику не передаются.

`available_actions` — tuple уникальных строк из `baseline`, `extra_trees`, `catboost`, `lightgbm`, `linear`. Пустой tuple допустим и возвращает `[]`. Проверяй аргументы даже при пустом списке доступных действий. `limit` — строго `int`, не `bool`, от 1 до 8. Для неверных типов и значений всех аргументов используй `ValueError`.

Кандидат содержит ровно пять ключей: `id`, `action`, `label`, `model_config`, `feature_config`. Конфигурацию модели создавай через `make_model_config`, признаки — через `normalize_feature_config`. Пример ID: `portfolio_v1_lgbm_conservative`. Порядок детерминирован; фильтрация по доступным действиям сохраняет его, затем применяется limit. ID уникальны, канонически одинаковые сочетания модели и признаков не повторяются. Возвращай независимые структуры, чтобы изменение результата не влияло на последующие вызовы.

Результат должен переживать JSON round-trip с `allow_nan=False`. Никаких объектов моделей, callable, NumPy-скаляров, путей, `seed`, `random_state`, `n_jobs`, `thread_count` или GPU-настроек. Не импортируй `TaskSpec`, CatBoost или LightGBM ради генерации списка. Доступность пакетов определяет вызывающая сторона. Вызов с `("baseline", "extra_trees", "linear")` должен работать без дополнительных модельных пакетов. Не добавляй новый общий модуль ради этого контракта.

## 4. Зафиксируй восемь гипотез

Используй следующий стартовый набор. Все перечисленные параметры разрешены текущим allowlist; остальные берутся из defaults. Для CatBoost и LightGBM в классификации исходно сохраняй отсутствие весов классов. Признаки по умолчанию стандартные, кроме последнего варианта.

| Кандидат | Настройки и проверяемая идея |
| --- | --- |
| `linear_regularized` | Ridge: `alpha=10`; LogisticRegression: `C=0.1,max_iter=1000,class_weight=None`. Дешёвая регуляризованная линейная альтернатива. |
| `baseline_conservative` | RF: `n_estimators=300,max_depth=24,min_samples_leaf=4,max_features=0.5,class_weight="balanced_subsample"`; HGB для регрессии: `max_iter=300,max_leaf_nodes=15,min_samples_leaf=40,learning_rate=0.05,l2_regularization=5`. Устойчивость более консервативных деревьев. |
| `et_regularized` | ExtraTrees: `n_estimators=300,max_depth=None,min_samples_leaf=4,max_features=0.5`; классификация: `class_weight="balanced"`. Снижение переобучения через листья и подвыбор признаков. |
| `cb_shallow` | `iterations=500,depth=4,learning_rate=0.05,l2_leaf_reg=10`. Неглубокий регуляризованный бустинг. |
| `cb_medium` | `iterations=500,depth=7,learning_rate=0.03,l2_leaf_reg=20`. Нелинейности при умеренной глубине. |
| `lgbm_conservative` | `n_estimators=400,num_leaves=15,max_depth=5,min_child_samples=40,learning_rate=0.05,reg_lambda=10,colsample_bytree=0.8`. Небольшие деревья и сильная регуляризация. |
| `lgbm_medium` | `n_estimators=500,num_leaves=63,max_depth=8,min_child_samples=60,learning_rate=0.03,reg_lambda=10,colsample_bytree=0.8`. Более сложные взаимодействия при достаточно крупных листьях. |
| `lgbm_representation` | Параметры `lgbm_conservative`; признаки `missing_indicators=True,rare_min_count=10`. Устойчивость обработки пропусков и редких категорий. |

До новых измерений допустима одна обоснованная корректировка набора; запиши её в пререгистрации. Не превращай задачу в широкий перебор. Зафиксируй статические пределы: 8 кандидатов, CatBoost до 500 итераций и глубины 7, LightGBM до 500 деревьев и 63 листьев, RF/ET до 300 деревьев, HGB до 300 итераций, LogisticRegression до 1000 итераций.

Для преобразований признаков проведи отдельную внутреннюю абляцию: исходный вариант, только индикаторы, только объединение редких категорий, оба преобразования. Это позволяет понять источник эффекта. Абляции не обязаны становиться дополнительными возвращаемыми кандидатами.

## 5. Проведи честные эксперименты

Основной контроль — нынешний `exploration_plan`: там уже восемь вариантов разных семейств. Покажи также стандартный baseline как ориентир. Сравнение только с одной слабой моделью недостаточно. Не объявляй результаты этого исследования оценкой полного production AutoML: его refinement и остальные этапы здесь не интегрируются.

До обучения сохрани manifest: commit, версии пакетов, fingerprints входов, точные конфигурации, порядок кандидатов, seeds разбиений, бюджеты, правило ранжирования и выбора. Заморозь внешние части **до** исследовательского выбора.

Итерация 1: реализуй контракт, небольшой smoke run и замеры стоимости. Итерация 2: проведи скрининг и абляции исключительно на inner-fit/inner-validation внутри outer-fit. Итерация 3: зафиксируй правила и оцени выбранный внутри кандидат каждого портфеля на внешней части. Любая дополнительная итерация должна отвечать на конкретный вопрос, а не продлевать работу.

Для классификации используй группировку по всем исходным признакам без ID и target. Точные дубли, включая строки с конфликтующими ответами, остаются в одной группе. Заранее выбери новые seed разбиений, например 1729 и 2718, и конкретные folds. Нужны несколько парных внешних проверок, где внутренний выбор повторяется независимо. Проверяй отсутствие пересечения групп и наличие всех классов в обеих частях. Невозможный fold фиксируется как ограничение; нельзя искать другой seed до удачного результата.

Для регрессии на публичной задаче используй rolling-origin по явно указанному `Year_Factor`. Обучение использует только прошлые периоды, внутренний holdout тоже находится внутри доступного прошлого. При недостатке истории оставь заранее заданный вариант либо явно пропусти адаптацию. Не перемешивай годы ради дополнительных folds.

Все преобразования обучаются заново на fit. Наружные ответы не используются для выбора признаков, параметров, кандидатов, порогов или остановки. Если несколько моделей сравниваются по outer и выбирается лучшая, этот outer стал selection; независимую оценку по нему заявлять нельзя. Результаты предыдущего внешнего fold не должны менять процедуру следующего.

Важно: команда уже видела все пять классификационных folds seed 42 и периоды регрессии 3–5 в документации. Новые seeds на том же публичном train не создают полностью независимый датасет. Различай вложенную честность текущего запуска и независимость от предыдущих исследований. Нового невиданного будущего периода регрессии здесь нет.

Добавь быстрые проверки переносимости на доступных в sklearn breast cancer, wine и diabetes. Они проверяют бинарную/многоклассовую классификацию и регрессию. Малые синтетические наборы с пропусками и неизвестными категориями подходят для технических стресс-проверок. Не выдавай их за доказательство качества на неизвестном соревновании. Девять метрик не являются девятью независимыми задачами; дополнительные метрики можно пересчитать по тем же прогнозам.

## 6. Измеряй качество вместе со стоимостью

Кандидаты запускаются последовательно. Политика ресурсов — `model_n_jobs=8`, общий предел OpenMP/BLAS 8; не запускай параллельно несколько восьмипоточных моделей. Существующий `LogisticRegression(n_jobs=1)` не меняй: BLAS ограничивается внешним контекстом. `build_pipeline` использует фиксированный модельный SEED; новые seeds здесь относятся к разбиениям, не к модельному JSON.

Сравнивай портфели при одинаковом wall-clock бюджете и одинаковом лимите попытки. Начальный ориентир: 600 секунд поиска, до 180 секунд на попытку, отдельный одинаковый бюджет финального refit. Подбери выполнимый бюджет по пилоту до сравнения и запиши его. Все inner-fit и абляции, влияющие на выбор кандидата, входят в бюджет соответствующего портфеля. Отдельные диагностические абляции можно измерить вне этого сравнения, но их результаты не меняют уже зафиксированного победителя и не выдаются за бесплатный этап поиска. Количество завершённых кандидатов может различаться — это часть результата. Равное число моделей само по себе не означает равную стоимость.

Используй существующий ограниченный subprocess и телеметрию, если подходят, не меняя их код. Задай явный конечный лимит памяти не выше существующего defaults. Сохраняй fit/predict/total wall time, CPU time и peak RSS процесса с потомками, когда доступны. Отмечай отсутствующую телеметрию. Timeout, OOM, ошибки и предупреждения сходимости остаются в отчёте.

Каждая попытка сохраняет конфигурацию, split hash, seed, ID/позиции строк, статус и исходные предсказания: actual, labels либо полный вектор вероятностей с порядком классов. Положительный класс не угадывай по номеру столбца. Используй существующие scorer и проверки вероятностей. После записи независимо пересчитай метрики из CSV. Проверь неизменность входных fingerprints.

## 7. Подготовь окружение, тесты и сдачу

Штатная подготовка в Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe prepare_data.py all
.\.venv\Scripts\python.exe dev_check.py
```

Существующую подходящую `.venv` не пересоздавай. На Linux/macOS первая команда — `python3.12 -m venv .venv`, путь интерпретатора — `.venv/bin/python`. Реальные task-файлы после подготовки: `data/regression/task.md` и `data/classification/task.md`. Для нового runner сделай документированный CLI с `--help`, путём задачи, новым output-каталогом, бюджетами и явными настройками проверки. Запиши фактически выполненные команды для обеих задач в отчёт.

Тестируй через используемый в проекте `unittest`:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_portfolio_recipes.py -v
.\.venv\Scripts\python.exe dev_check.py
```

Покрой девять метрик, неверные профили, неизвестные действия, пустую доступность, strict limit, уникальность, JSON, независимость объектов, конфигурационные ограничения и fallback без CatBoost/LightGBM. Небольшие реальные fits проверяют регрессию, бинарные/многоклассовые вероятности и fold-local preprocessing. Тяжёлые эксперименты не должны запускаться unit-тестами. Если нет доступа к репозиторию, интерпретатору или данным, не придумывай выполненные команды, результаты и зелёные тесты: укажи ограничение и передай Тане точные команды продолжения.

В компактном Git-отчёте покажи парные inner/outer результаты, абляцию, затраты, неудачи и практическую рекомендацию. Для Macro F1 отдельно покажи поддержку редких классов: прежний эффект был чувствителен к единичным объектам Worms. Не усредняй разные метрики в произвольный общий балл. Для временных folds покажи отдельные периоды и разброс. Если считаешь интервалы, учитывай группы дублей. Укажи команды, пути и SHA-256 тяжёлых артефактов, чтобы их можно было передать отдельно.

Перед сдачей проверь `git diff --check`, состав diff и отсутствие данных/секретов. Коммить явно только четыре разрешённых файла. Push своей ветки и создай PR в `main` с описанием гипотез, результатов, ограничений и выполненных проверок. Не включай automerge, не сливай PR и не делай force-push. Если публикация недоступна, передай команды и готовое описание PR. Заверши кратким итогом: что реализовано, что измерено, что не подтверждено и какие рецепты рекомендуются интегратору. Устойчивого выигрыша может не быть — тогда сохрани доказательства и честно рекомендуй не менять текущий портфель.
