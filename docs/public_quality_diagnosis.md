# Диагностика качества после ответа организаторов

Это повторный анализ сохранённых предсказаний на публичном **TRAIN**, а не
платформенного test. Новых обучений и запросов API нет. Данные уже использовались
в разработке; независимым подтверждением качества эти проверки не являются.

Организаторы сообщили, что в отправке 03:39 одна задача не превзошла бейзлайн и
получила ноль. Тип этой задачи, её метрика, реальное время работы и ответы Qwen
пока неизвестны. По общему public-баллу это восстановить нельзя. PR14 и PR15 не
входили в проверенный ZIP исходного `3908292`.

## Проверка фактических контрактов

На официальных публичных `task.md` код `3908292` корректно определяет:

| Задача | Метрика | Автоматическая проверка | Размер outer fit / validation |
|---|---|---|---:|
| Регрессия | RMSE | Последний период `Year_Factor`, обучение только на прошлом | 35000 / 18308 |
| Классификация | Macro F1 | StratifiedGroupKFold по одинаковым исходным признакам | 70155 / 17515 |

Признаки без ID/target, группы считаются до предобработки. Для классификации
автоматический seed 42/fold 0 даёт нулевое пересечение групп, все 10 классов в
обеих частях; Worms в проверке 16 строк. Регрессия: train-периоды 1–5, test 6,
поэтому последний доступный период 5 используется для локальной проверки.
Парсинг неверной метрики или случайный split для этих двух описаний здесь не
воспроизведён. Это не означает, что любая другая задача распознаётся без ошибок.

## Повторный расчёт метрик из сохранённых CSV

Стенд PR14 исследовал baseline `3908292` и candidate `ac628cf`; отправлен был
baseline. `diagnose_public_evidence.py` повторно прочитал все 8 CSV. Проверены
seal/manifest, SHA файлов ответов и предсказаний, порядок literal IDs и точное
совпадение пересчитанной метрики с исходным аудитом (допуск 1e-10).

| TRAIN audit | Baseline | PR14 candidate | Единица |
|---|---:|---:|---|
| Регрессия, период 4 | 44.761238 | 55.244543 | RMSE |
| Регрессия, период 5 | 48.994980 | 43.980237 | RMSE |
| Классификация, seed 1729 / fold 0 | 0.619064 | 0.631039 | Macro F1 |
| Классификация, seed 2718 / fold 0 | 0.619291 | 0.642213 | Macro F1 |

Ухудшение PR14 на периоде 4 вызвано описанным в его отчёте чрезмерным резервом
планировщика: поиск не допустил кандидатов. Оно не является причиной уже
полученного платформенного балла, поскольку эта версия не была отправлена.

### Классификация: ошибки редких классов

У двух baseline-прогнозов Macro F1 почти одинаков, но ошибки существенно разные:

| Метрика / класс | Seed 1729 | Seed 2718 |
|---|---:|---:|
| Accuracy | 0.825542 | 0.781480 |
| Weighted F1 | 0.829824 | 0.804332 |
| Macro F1 | 0.619064 | 0.619291 |
| Analysis F1 | 0.327402 | 0.205917 |
| Backdoor F1 | 0.218905 | 0.134777 |
| Worms F1 | 0.300000 | 0.611111 |
| Worms support | 16 | 16 |

У второго прогноза для Backdoor precision 0.0866 при recall 0.3043; у первого
precision 0.6875 при recall 0.1302. Усиление весов редкого класса поэтому не
равнозначно улучшению его F1. Наиболее многочисленные ошибки — Exploits/DoS и
Normal/Fuzzers. Для Macro F1 важны также редкие классы: шум 16 проверочных
строк Worms может заметно менять среднее по классам.

Вывод для новых экспериментов: сохранять вероятности и отчёт по каждому классу,
сравнивать варианты весов по Macro F1 на одинаковых группах, не выбирать модель
по accuracy. Отдельные правила порогов должны иметь собственную calibration и
selection; подгонять их на outer audit нельзя.

### Регрессия: вклад хвостов в RMSE

| Ошибка baseline | Период 4 | Период 5 |
|---|---:|---:|
| RMSE всех строк | 44.7612 | 48.9950 |
| Доля SSE у 1% строк с наибольшей ошибкой | 53.14% | 34.11% |
| Доля SSE у верхнего 1% истинного target | 50.72% | 29.37% |
| RMSE верхнего 1% истинного target | 318.12 | 264.86 |
| RMSE остальных строк | 31.58 | 41.38 |
| 99-й процентиль target / prediction | 300.96 / 224.62 | 290.86 / 252.52 |

SSE — сумма квадратов ошибок. Модели заметно сглаживают высокие значения.
Автоматический log-target или обрезка высоких ответов могут ухудшить RMSE,
даже улучшая относительную ошибку типичных строк. Более длинный boosting с
обычным squared-error objective имеет смысл проверить, но результат нельзя
гарантировать заранее. Дополнительные RMSE по периодам нужны из-за смены
распределения; inner-победитель прошлого периода не обязательно лучший в будущем.

## Приоритеты и границы вывода

1. Получить у организаторов отдельные RMSE/Macro F1, baseline-метрики, время
   работы и API-счётчики. Этим анализом не установлено, какая задача дала ноль.
2. Сравнить новый CPU-профиль с контролем в одинаковом бюджете и с замороженными
   inner/outer split. Сначала выбирать по inner, затем один раз считать outer.
3. Проверить более длинные CatBoost/LightGBM с сохранением простых моделей
   в контроле. Больший каталог без правильного отбора уже не показал устойчивого
   преимущества в `portfolio_recipes_report.md`.
4. Учитывать остаток времени после остановки LLM, сохраняя проверенный CSV и
   резерв на полный refit. Новые ресурсы не устраняют программную раннюю остановку.

Полезный вывод о качестве здесь есть; доказательства отказа Qwen, нехватки
памяти/CPU или будущего private score нет. Для нового профиля нужен отдельный
парный benchmark. Новая группа/seed всё равно не делает ранее исследованный
публичный датасет полностью независимым confirmation.
