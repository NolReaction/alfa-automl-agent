# Ранний допуск кандидатов: проверка порядка поиска

База: `d05572846369f3b1e9cfa33f4008dda028db4fe0`, main на 22 октября 2026.

## Изменение

В длинном adaptive-маршруте временной регрессии extensions теперь выполняются
после измеренного baseline и перед очередью обычных локальных рецептов.
Для раннего запуска нужны совпадающие INNER/outer time policy и имя периода.
Раньше до этого hook
нужно было закончить весь warmup; один дорогой fit мог оставить все расширения
без времени. Временная регрессия сначала проверяет историю, затем LightGBM
и CatBoost. Классификация и прочие разбиения сохраняют исходный поздний hook
и порядок кандидатов.

Фабрики, defaults, INNER-разбиение, caps 64 ordinary + 6 custom,
исходный дедлайн и правила принятия/финализации сохранены. После расширений
обычный поиск продолжает прежнюю очередь в оставшееся время. Ранний запуск
может изменить доступного finalist и расход времени, поэтому native сравнение
измеряет итог системы с новым порядком; одинаковые recipe hashes всех fits
между arms не предполагаются. Ранний ensemble может штатно пропуститься.

Прямые low-level вызовы сохраняют старый порядок по умолчанию:
`extensions_first=False`, `prioritize=False`. Native v3 явно включает новую
политику только для подходящей временной регрессии.

## Доказательства

`run.json.local_research` сохраняет `extension_schedule`, факт вызова hook
и остаток времени до/после него. `research_extensions.schedule/order` показывает
фактический порядок, а отдельные trials — frozen hashes, попытку и host feedback.
Вызов hook не равнозначен обучению, победе на outer или публикации.

Статический summarizer не запускает solver, не расходует API и не редактирует
входные отчёты:

```powershell
.\.venv\Scripts\python.exe experiment_rescue_integration_report.py --reports C:\ar\run.json --output C:\ar\summary.json
```

Отсутствующие счётчики/время остаются null. Сводка не заменяет проверку receipts,
пересчёт метрики из CSV и аудит дочерних процессов. Ресурсная квалификация
не выводится из одного успешного native отчёта.

Поля `frozen_baseline` и `frozen_candidate` сохраняют заявленные в native
отчёте `code_hash`/`recipe_hash`. `candidate_receipts` сохраняет указанные там
пути `outer`/`refit` и хеши кода/рецепта, с пометкой
`verification="not_performed"`. Это скопированные метаданные: summarizer
не открывает указанные файлы и не сверяет их байты, nonce, входы или CSV.
При отсутствии этих объектов сохраняется null. Хеши самих receipt-файлов
из хешей кода/рецепта не выводятся.

## Сравнение

Парные прогоны на обеих публичных задачах выполняются последовательно,
без API, с фиксированным бюджетом 900 секунд на arm. Классификация использует
один manifest `score_meter`: grouped fit 70155, внешний holdout 17515,
group overlap 0. Регрессия также требует native полного TRAIN, поскольку
derived-task с меньшим числом периодов меняет условия history discovery.

Окружение локальной проверки: Python 3.12, pinned core/CB/LGB из requirements,
квота 8 CPU и 8 GiB RAM. AutoGluon не установлен. Это не полная квалификация
официального окружения с 32 GB и AutoGluon и не оценка скрытого теста.

### Почему ранняя классификация не включена

Первый экспериментальный runtime `c7e902d95ae82889324e0642d4fae028ce22052d`
включал ранний hook для всех задач. В classification grouped holdout:

| Arm | Macro F1 итогового CSV | Секунды процесса | Опубликованная модель |
| --- | ---: | ---: | --- |
| main `d055728` | 0.6221456784403092 | 798.459 | ordinary LightGBM finalist |
| ранний hook `c7e902d` | 0.6270856862525388 | 864.692 | исходный FixedBlend baseline |

Одинаковые входы/разбиения и исходный frozen baseline подтверждены. Но вклад
класса Worms (16 holdout-строк) в delta Macro F1 равен +0.008523; остальные
девять классов суммарно дали −0.003583. Это не устойчивое доказательство
улучшения классификации, поэтому итоговая native-политика для неё сохранена.

В раннем опыте LightGBM extension дал INNER 0.607614, CatBoost — 0.509536 за
264.435 секунды. Frequency дал 0.620115, но был отклонён по `refit_budget`;
он не публиковался. Число достигнутых расширений не равно улучшению результата.
Независимая проверка опубликованного baseline подтвердила полный fit на 70155
строках, 17515 TEST-ID, nonce/phase/hash receipts и совпадение итогового CSV.
Процесс завершился с кодом 0, API-запросов 0; RSS/cleanup остаются неизвестными.

Регрессионная пара выполняется отдельно на полном native TRAIN. До её
завершения выигрыш регрессии и готовность ранней политики к выпуску не заявляются.
