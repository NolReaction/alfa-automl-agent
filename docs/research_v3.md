# Research v3: исследование и внешняя проверка

Исходная версия: `ccdf49e333495d496ee3a712571199e493d790d4`.
Документ описывает новый протокол; старые отчёты v2 сохраняют прежнее
происхождение и не получают задним числом гарантий v3.

## Воспроизведённая проблема v2

В `ResearchValidation` v2 manifest объявляет `data_directory`, `fit_rows` и
`validation_rows`, но в соответствующем `train.csv` остаются **все** исходные
ответы. Обычное чтение train с выбором validation_rows показывает outer-target.
В `RunState.consider` внешняя метрика и диагностика затем включаются в tool
feedback и историю следующего запроса. Корректный пересчёт CSV управляющим
процессом не проверяет, использовались ли эти ответы при EDA или выборе модели.

Риск воспроизведён без API на синтетическом CSV:

```bash
.venv/bin/python -m unittest tests.test_research_workspace.ResearchWorkspaceTests.test_v2_fixture_reproduces_visible_outer_answers -v
```

Тест читает **обычный объявленный вход** v2, а не обходит ограничения по
нестандартному пути. И ID, и ответы внешней проверки доступны этому коду.

## Границы данных и стадии

| Стадия | Входы обучающего кода | Назначение оценки |
| --- | --- | --- |
| Подготовка host | Исходные train/test, схема, метрика | Закрепить outer split и снимок ответов |
| Внутренние эксперименты | Только outer-fit; inner fit/validation внутри него | `selection`, для гипотез и параметров |
| Фиксация | Выбранный Python и JSON-рецепт | Зафиксировать код/параметры и их хеши |
| Внешняя проверка host | Outer-fit с ответами и outer-holdout без ответов | `final_check`, сравнить два заранее фиксированных рецепта |
| Полное обучение host | Полный train и исходный test без ответов | `refit`, получить конкурсный CSV |
| Публикация | Проверенный CSV выбранного результата | Атомарно сохранить допущенный результат |

Код исследования не обучается на полном train перед фиксацией. После начала
внешней проверки новые API-запросы, гипотезы и изменение рецепта запрещены.
После полного refit исследовательский диалог также не возобновляется.

Сравнение baseline и кандидата по outer является **выбором по outer**. Даже
если каждый рецепт фиксирован заранее и внешняя оценка проводится один раз,
оценка сохранённого победителя не становится несмещённой независимой оценкой
системы. Отчёт должен сохранить обе оценки и факт этого выбора. Для независимой
оценки выбранной системы нужна ещё одна неиспользованная часть либо платформа.

Ранее просмотренные командой public-разбиения уже участвовали в исследовании.
Новый seed или nested split не отменяет эту историю и не делает их новыми
независимыми тестами.

## Разрешённое исследовательское представление

`ResearchWorkspace` получает исходную задачу и создаёт отдельную рабочую папку:

```text
task.md
research_validation.json
data/train.csv
data/test.csv
data/data_dictionary.csv
data/sample_submission.csv
```

Здесь train содержит только outer-fit. Исследовательские test и template
составлены из inner-validation строк этого же outer-fit. Исходный конкурсный
test, outer-holdout и его ответы в это представление не копируются. Task.md
синтезируется из проверенной метрики, типа задачи и схемы классов; исходные
абсолютные пути, прежние результаты и свободный текст исходного task.md туда
не переносятся. Это сознательное ограничение поддерживаемого CSV-контракта.
Явная дополнительная гипотеза из поля Alfa Lab сохраняется отдельно как
ограниченный пользовательский совет (до 500 символов), с требованием проверять
его только на разрешённых данных и inner validation. Остальной свободный текст
не передаётся автоматически.

На стороне host остаются исходный `TaskSpec`, raw train/test, outer позиции,
ID/ответы, исходный fingerprint и схема. Рабочий `research_spec` сохраняет
порядок output columns, классов, probability columns и positive class, но
связан с разрешёнными рабочими путями. CSV читаются со строковыми ID и метками,
включая `NA` и ведущие нули.

Manifest v3 объявляет stage/research, purpose/selection, allowed_inputs,
training_data_scope/outer_fit_only, схему признаков/метрики/классов,
inner fit_rows и validation_rows, прогнозные колонки и требуемые артефакты.
Outer позиции, ID, ответы, их хеши и outer-score в manifest не входят.
`holdout_columns` v3 являются прогнозным CSV-контрактом TaskSpec: колонка
actual от исследователя больше не требуется.

При автоопределении времени/групп host закрепляет стратегию до экспериментов.
Внутреннее разбиение повторяет её **только внутри outer-fit**. Для запуска
существующего AutoML на рабочем task необходимо явно передать эту `choice`:
синтетический test не должен заново переопределять временную стратегию.
Любые внутренние оценки baseline, включая названный им outer holdout,
на этом представлении остаются `selection` относительно внешнего протокола v3.

Если inner split невозможен, manifest содержит `inner_unavailable_reason`
и пустые inner индексы. Использовать внешний holdout для подбора вместо него
нельзя. Host может сохранить заранее фиксированный нетюнингованный рецепт
или честно завершить доступным fallback.

## Исполнимый кандидат

Исследователь предоставляет `research_candidate.py`, `research_recipe.json` и
`research_hypothesis.json`. Предполагаемый интерфейс модуля:

```python
def fit_predict(X_fit, y_fit, X_predict, context):
    return {"predictions": predictions, "classes": prediction_classes}
```

`X_fit` и `X_predict` содержат только raw признаки, `y_fit` только разрешённые
ответы fit. Context версии 3 передаёт фазу, фиксированный рецепт и схему
numeric/categorical/classes/positive class/metric. Для вероятностей порядок
`classes` явный. Host запускает модуль в отдельном Python-процессе, а не
импортирует сгенерированный код в основной процесс. Он задаёт файлы входов,
таймаут и порог памяти, проверяет хеши кода/JSON и прогнозный CSV по TaskSpec.
Ответы для подсчёта метрик не сериализуются в процесс внешнего прогноза.

Файлы рабочего каталога не считаются доказательством сами по себе: кандидат
копируется в host checkpoint до внешней оценки. Между validation/refit код и
JSON-рецепт неизменны. Подмена входов, порядка ID, старые артефакты, неизвестные
классы, неправильные вероятности и неконечные числа отклоняются. Итоговый CSV
публикуется только после host-проверки.

Точный контракт включён в `manifest.candidate_contract`. Оба X являются
`pandas.DataFrame` с raw string признаками: ID и target в них отсутствуют.
`y_fit` является `pandas.Series`: числа для regression, точные строки для
classification. Результат является dict только с ключами `predictions` и,
необязательно, `classes`; `predictions` обязателен всегда, а `classes`
обязателен для вероятностей и является непустым list/tuple строк в порядке
прогнозных колонок. Строки результата строго соответствуют порядку X_predict.
CSV и ID оформляет host. Лимиты файлов: код до 256 KiB, JSON-рецепт до 64 KiB.

Context дополнительно содержит version/protocol_version, nonce и code/recipe
hashes. Фазы `inner_selection`, `outer_validation`, `full_refit` соответствуют
назначениям `selection`, `final_check`, `refit`; исполнение также принимает
эти три канонических имени. Кандидат должен использовать аргументы для
обучения и не менять поведение по фазе; это правило протокола, а не
доказательство отсутствия любого условного поведения произвольного Python.

## Проверяемые инварианты

1. После фиксации outer индексов, схемы и порядка классов изменение
   outer-target не меняет ни одного байта разрешённых входов, inner split и
   inner-ответов. Оно может изменить последующий final_check и приёмку.
   До фиксации split метки законно участвуют в стратификации.
2. Внешний результат не включается в следующий prompt: после final_check
   следующего исследовательского запроса вообще нет.
3. Препроцессинг обучается только на переданном fit; time идёт из прошлого
   в будущее, группы одинаковых raw признаков не пересекаются.
4. Полные ответы передаются исполнимому кандидату только после фиксации;
   хеши кода и рецепта одинаковы при final_check и refit.
5. Inner/final_check/refit различимы в отчёте. Unknown metric или только
   структурно правильный CSV не означают проверенное качество.
6. Ошибка API/процесса/refit и худший кандидат сохраняют последний действительно
   допущенный CSV. Без него ложный успешный статус недопустим.

Локальная проверка разрешённого представления:

```bash
.venv/bin/python -m unittest tests.test_research_workspace -v
```

Тесты проверяют воспроизведение v2, байтовую инвариантность v3 при
интервенциях regression/classification outer-target, time/group ограничения,
девять метрик, многоклассовые вероятности, точные строковые метки, неправильные
ID/числа/входы и невозможность inner split. Реальные API-запросы не нужны.

## Предел гарантии

Раздельные файлы и контроль протокола защищают от обычного случайного
подглядывания. Python под тем же пользователем ОС способен искать другие
пути и обращаться к ним. Это **не полноценная OS-песочница** и не доказательство
изоляции от злонамеренного кода. AST-фильтры и fingerprint-проверки не меняют
этот факт; контроль целостности не является контролем чтения файлов.

Ограничения времени/измеряемого RSS и очистка дерева процессов сохраняются,
но не заменяют OS-изоляцию. Политика работы с произвольным недоверенным кодом
потребует отдельной проверенной реализации на Linux и Windows.

Исследовательский task содержит проверенные метрику, тип задачи, схему и классы,
а также цитируемый обзор исходного описания до 4 KiB UTF-8. Полное очищенное
описание сохраняется в `task_description.md`, входит в allowed inputs и проверку
целостности. Ссылки на четыре CSV перенаправлены в разрешённые представления,
известные исходные пути и распознанные секреты удалены. Словарь признаков сохраняет
все колонки. Исходное описание трактуется как условия задачи и не заменяет
host-контракт исследования.

До 256 KiB очищенное описание сохраняется целиком. Более длинное условие явно
помечается неполным: адаптивный поиск и API отключаются, применяется фиксированный
базовый рецепт. Это ограничение отражено в `task_semantics`, без молчаливого
усечения. Сохранение текста позволяет исследователю учитывать предметные условия,
но не доказывает поддержку любого нового типа задачи или неизвестной метрики.

## Измеренное время и обратная связь

Host измеряет полное исполнение каждого замороженного рецепта, включая подготовку
входов, и хранит оценки отдельно по хешам кода и конфигурации. `BudgetPolicy`
сохраняет исходный дедлайн; резерв не меньше прежних 30% и увеличивается по
измеренным длительностям и размерам выборок. Предел масштабирования и запас
обозначены как эвристика, а не гарантия времени обучения. Рецепт с улучшенной
inner-метрикой, который по оценке не успевает пройти финализацию, получает
`refit_budget` и не заменяет принятый рецепт.

Внешние проверки и оба возможных refit распределяют оставшееся время совместно,
с приоритетом сохранения базового результата. Перед каждым этапом план
пересчитывается. Подготовка CSV, запуск дочернего процесса и обязательная проверка
результата учитывают срок этапа и абсолютный дедлайн; сам лимит платформы остаётся
последней границей выполнения.

Каждый запрос получает свежую сводку оставшегося бюджета. После inner-эксперимента
исследователь получает агрегированную диагностику, вычисленную host по закреплённым
предсказаниям: смещение и квантили ошибок регрессии либо показатели классов и
основные путаницы классификации. Размер сводки не превышает 8 KiB; исходные строки
и ID в неё не входят. Outer/refit результаты этим API диагностики не принимаются.
Необязательная диагностика не отменяет уже проверенную метрику.
