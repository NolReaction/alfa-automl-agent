**3. Реализуй зафиксированный контракт адаптера.**

В `agent/history_candidate.py` реализуй именно этот публичный интерфейс:

```python
def fit_history_candidate(
    *,
    task_type: str,
    metric_name: str,
    feature_columns: tuple[str, ...],
    X_raw: pd.DataFrame,
    y,
    config: dict | None,
    blend_weight: float,
) -> "FittedHistoryCandidate":
    ...

class FittedHistoryCandidate:
    def apply(
        self,
        X_raw: pd.DataFrame,
        base_prediction: np.ndarray,
    ) -> "HistoryApplication":
        ...

@dataclass(frozen=True)
class HistoryApplication:
    prediction: np.ndarray
    applied_mask: np.ndarray
    diagnostics: dict
```

Интерфейс согласован для параллельной интеграции. Не переименовывай функции, аргументы и поля, не добавляй обязательные аргументы односторонне. Необходимое изменение предложи Диме до реализации. Внутренние помощники и небольшой класс конфигурации разрешены.

Конфигурация JSON-совместима. Пример для публичной regression:

```json
{
  "key_columns": ["State_Factor", "building_class", "facility_type", "floor_area", "year_built", "ELEVATION"],
  "period_column": "Year_Factor",
  "numeric_columns": ["floor_area", "year_built", "ELEVATION"],
  "positive_columns": ["year_built"],
  "ambiguity_policy": "allow"
}
```

Поддержи явные политики `allow` и `past_unique_only`; остальные значения отклоняй. Вторая разрешает историю только при отсутствии повторов ключа внутри доступных прошлых периодов. Числовой вес истории передаётся отдельно и принадлежит `[0, 1]`.

Обязательные правила:

- `config=None` отключает историю. Знакомые названия колонок не включают её автоматически. Ключ и числовой период поступают из явно согласованной конфигурации кандидата. Числовая колонка сама по себе не доказывает временной смысл.
- Не выводи ключ из `id`, названия файла, target или схемы публичной задачи. Статистическое предложение ключа допустимо только как диагностика для последующего решения человека. Совпадение эвристического ключа не доказывает идентичность объектов.
- Все ключевые колонки и период должны входить в `feature_columns`. Target и технический ID не должны передаваться интегратором как признаки; адаптер проверяет предоставленный список.
- Классификация, неизвестный тип задачи, неподдерживаемая метрика, отсутствие конфигурации или необходимых колонок дают неактивного кандидата с явной причиной. Не определяй regression по числовому dtype target. Для известной regression сохраняй целевую метрику; не подменяй MAE/MSE/R2 метрикой RMSE.
- Ошибочная явная конфигурация, дубли ключевых колонок и невалидный вес вызывают понятную ошибку. Не прячь программные ошибки под общим `except Exception` с возвратом baseline.
- При неактивном кандидате прогноз сохраняется без изменений, включая dtype, форму и порядок classification labels/probabilities; `applied_mask` содержит False для каждой строки.
- В regression формула — `(1 - blend_weight) * base_prediction + blend_weight * past_mean`. Прогноз остаётся непрерывным в исходной шкале цели: без порогов, округления или clipping. Вес истории не является весом класса или общего ансамбля.
- При отсутствии допустимой истории прогноз строки в точности равен baseline. При весе 0 равен весь массив. Не выполняй арифметику с `NaN` для неактивных строк.
- Источник ключей и периодов — raw-значения до преобразования признаков модели во float. Не округляй, не склеивай ключ строковым разделителем, не объединяй пропуски с буквальным `"NA"`. Сохрани и опиши правила текстовой нормализации.
- Поддержки числовых периодов достаточно; даты и локали не угадывай. При невалидном периоде используй явно документированный отказ от истории без потери строк.
- Каждая строка видит исключительно fitted-ответы строго меньших периодов. `apply()` не принимает ответы, не дообучается и не меняет fitted state. Входы, число строк и соответствие прогнозов строкам сохраняются.

В `diagnostics` укажи статус, причину отказа, число строк, покрытие полным ключом, прошлой историей, неоднозначной прошлой историей и применённой смесью. `applied_mask` обозначает строки, где разрешена и применена смесь с ненулевым весом; число фактически отличающихся прогнозов можно показать отдельно.

Checker сейчас учитывает повторы в проверяемом году при определении `clean`, encoder — только прошлые повторы. Не подмени одно другим: рабочая политика применимости опирается на прошлое, чтобы прогноз строки не менялся от размера query-батча. Повторы в query оставь отдельной диагностикой.

**4. Проведи исследование с честным выбором параметров.**

До новых запусков запиши небольшую матрицу гипотез: baseline без истории; прежняя фиксированная смесь 0.5; вес, выбранный на внутренних временных разбиениях; политика `past_unique_only`. Сравнение с моделью, сохраняющей `Year_Factor`, отделяет удаление периода от эффекта истории. Существующий HGB с историческими признаками допустим как дополнительный ориентир. Не раздувай перебор без исследовательской причины.

Для внешнего года `t` из `{3, 4, 5}`:

1. Внешний train содержит только периоды `< t`.
2. Внутренние последовательные проверки строятся только внутри этого train.
3. На каждом inner-split заново обучаются базовая модель и encoder только на его прошлом.
4. Вес выбирается по внутренним прогнозам и метрике задачи.
5. После выбора модель и encoder обучаются заново на полном outer-train.
6. Внешние ответы используются только для оценки зафиксированного решения.

Повторное использование модели, уже обученной на полном outer-train, для получения inner-прогнозов запрещено. Заранее задай небольшую сетку весов с 0 и 0.5, правило равенства оценок и fallback при недостатке периодов. Если выбираешь политику неоднозначности, её выбор тоже происходит внутри train либо она оценивается как заранее фиксированный отдельный рецепт.

Эксперимент должен реально вызывать новый адаптер, а не содержать вторую копию смешивания. Все сравнения используют одни внешние строки. Сохраняй выбранные веса, внутренние оценки, периоды split, прогнозы, срезы покрытия, параметры, длительности и хеши. Объединённый RMSE вычисляй как `sqrt(sum(SSE) / sum(N))`.

Добавь парные доверительные интервалы разницы с baseline с одинаковыми bootstrap-выборками для сравниваемых прогнозов. Основной разумный вариант — группировка по ключу, сохраняющая вместе повторяющиеся строки между годами; строки без ключа обрабатывай по явно описанному правилу. Bootstrap строк можно оставить анализом чувствительности. Объясни, что интервалы условны на полученных прогнозах и не охватывают переобучение модели, выбор будущего года или уже выполненный перебор рецептов.

Покажи все результаты, включая ухудшения, отдельно для строк с историей, без неё и с неоднозначными совпадениями. Для малых срезов укажи размер и недостаточность доказательств. Не называй выбор окончательного рецепта по годам 3–5 независимой оценкой будущего качества.

Обучения и синтетические замеры запускай последовательно, максимум 8 потоков, без параллельных восьмипоточных fit. До эксперимента зафиксируй конечные лимиты попытки, полного запуска и памяти. Начальный ориентир: до 300 секунд на fit, 7200 секунд на исследовательский запуск и 8 GiB суммарного RSS дерева процессов, не выше доступной памяти машины; при иных значениях запиши причину до сравнения. Используй существующие helpers ограниченного subprocess, не меняя общий код. Время всех inner-refit входит в бюджет; timeout/OOM и неполные сравнения остаются в отчёте. Рост синтетики тоже ограничен общим deadline и памятью.

**5. Проверь причинность, отказ и стоимость.**

Нужны проверки конкретных рисков, а не заданное количество тестов:

- изменение outer-validation target не меняет inner-выбор веса, историю и прогнозы этого validation;
- будущие ответы не меняют более ранние признаки; ответы того же периода исключаются целиком;
- модели и encoder внутри nested-проверки действительно получают только свой train;
- неизвестные/неполные ключи, отсутствие истории и отключённая конфигурация сохраняют baseline;
- классификация и неизвестная схема не активируют историю;
- перестановка строк, другой query-батч и повторный `apply()` сохраняют соответствующие результаты;
- большие целые, близкие десятичные значения, дробные периоды и разделители внутри ключа не создают ложных совпадений;
- повторный fit забывает прежние данные; входы и выходные файлы защищены.

Проведи положительный синтетический контроль с известным сигналом и отрицательный — с разрушенной связью ключа и прошлой цели. Нулевой контроль проверяет методику; он не доказывает безопасность истории на любых данных. Измерь время и доступным способом пиковую память encoder на официальных данных и синтетике с растущей длинной историей одного ключа.
