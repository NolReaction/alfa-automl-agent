# Релиз восстановления и объединение исследований

В релиз входят Research v3, Windows-исправления и экспериментальные модули
из PR #12 и #13. Восстановление сохраняет исходный общий дедлайн задачи.
Новый запуск обучения не получает ещё один полный бюджет после ошибки.

## Что происходит при отказе

1. Перед основным решением `solution.py` готовит резервные предсказания для
   **исходного test**. Они рассчитаны по полному train: медиана для MAE,
   среднее для остальных поддержанных регрессионных метрик, частоты классов
   либо самый частый класс для классификации. Это обученный target prior с
   непроверенным качеством, а не копия `sample_submission.csv`.
2. Подготовка получает максимум 30 секунд и 5% остатка общего времени. Worker
   читает ID и target порциями, проверяет ID, сохраняет точные метки и порядок
   выходных столбцов. Дерево worker имеет мониторинг памяти с лимитом 2 GiB.
   API-ключи в его окружение не передаются.
3. CSV проверяется по контракту, исходным test IDs, хешам входов и receipt.
   Ожидаемые хеши CSV и receipt остаются у родительского процесса в памяти.
   Артефакты находятся под `.agent_runs/<uuid>/`; `emergency.json` отдельно
   обозначает `kind="target_prior"`, `quality_verified=false`.
4. В `auto` отсутствие части API-настроек либо ошибка создания клиента
   приводит к offline-поиску с остатком исходного времени. Явные
   `--mode llm` и `--check-api` сохраняют диагностику настройки API.
5. V3 допускает один дополнительный запрос на весь запуск для типизированного
   транспортного сбоя, таймаута, HTTP 5xx либо 429 без признаков исчерпанного
   баланса/квоты. Каждый запрос заново проходит guards времени, количества
   requests и контекста. SDK остаётся с `max_retries=0`. Ошибки авторизации,
   оплаты и уже полученные некорректные ответы не повторяются.
6. При полном отказе API продолжается ограниченный локальный поиск. После
   заморозки рецептов выполняются outer и refit; outer-ответы не возвращаются
   в исследовательский диалог. Провал кандидата позволяет вернуться к baseline.
7. Неожиданная операционная ошибка сохраняет принятый checkpoint, если
   неизменны оригинальные данные, разрешённое представление и закреплённые
   артефакты. Успешное восстановление обозначается `fallback`, не успехом LLM.
   Аварийный prior используется, когда принятого основного результата нет.

На восстановление оставляется небольшой резерв внутри того же лимита времени.
Проверка и копирование аварийного результата получают исходный абсолютный
дедлайн. Подмена данных, snapshot, frozen-рецепта или принятого checkpoint
не превращается в успешный результат. Файловые проверки не являются
OS-песочницей для произвольного кода того же пользователя.

## Что объединено из двух PR

- **PR #12:** отдельный портфель модельных рецептов и runner вложенных проверок.
  Результаты регрессии смешанные, стоимость классификационного поиска выше.
  Модуль включён в исходники, автоматического подключения к поиску нет.
- **PR #13:** отдельные правила Macro F1, регуляризация и допуск на независимой
  части calibration. В релизе дополнительно запрещены datetime/timedelta
  вместо вероятностей; F1 использует память O(N + K). На платформенных версиях
  библиотек отдельно повторены девять проверок: 2 улучшения, 7 identity-ничьих,
  0 ухудшений. Это изученные синтетические семейства, не private score.
  Перенос на полный host refit и production-подключение пока не выполнены.

`--metric-recipes` и `--stability-splits` также остаются явными опциями.
Добавление исследовательских файлов в main не означает включение новых
экспериментальных стратегий в конкурсный запуск.

## Проверки релиза

Целевые тесты проверяют transient retry, неповторяемые ошибки, guards бюджета,
клиентский bootstrap fallback, источник/receipt/CSV tampering и сохранение
принятого результата. Тесты извлечённого архива запускают точную команду
`python solution.py task.md` с локальным HTTP 503 и ошибкой конструктора SDK.
Проверяются ранний резерв, полный refit, receipts, неизменность исходных данных
и конечный CSV. Настоящие запросы к конкурсному сервису в этих тестах не нужны.

Evidence полного `research_api_failure` теперь имеет версию 2: две имитированные
ошибки соединения и один учтённый повтор. Исторические измерения evidence v1
с одной попыткой относятся к предыдущим исходникам.

ZIP собирается штатным `build_submission.py`: только корневые `.py` и
официальный `requirements.txt`. Пакет `agent` представлен корневыми модулями
и manifest loader. Данные, экспериментальные отчёты, модели, секреты,
интерфейс приложения и архив доказательств портфеля в ZIP не входят.

Два нулевых результата на скриншоте платформы не устанавливают причину сбоя.
По колонке длительности загрузки нельзя определить worker exit code,
ошибку API или качество по задачам. Для этого нужны метрики/логи проверки.
