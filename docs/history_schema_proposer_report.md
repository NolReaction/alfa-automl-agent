# Генератор схем истории: контракт v1, эксперимент и ограничения

Задание: `docs/team_round3/MURAD_HISTORY_SCHEMA.md`. Модуль `agent/history_schema_proposer.py` по сырым
INNER-fit признакам предлагает до четырёх структурно допустимых конфигураций истории для следующей INNER-проверки
хостом. Он не видит y, test, outer, путей, метрики и API, ничего не обучает, не выбирает вес и сам ничего не
включает (`auto_activate: false`). `identity_verified` всегда `false`.

## Итог

- Hard contract без нарушений: 0 в audit (39 запусков: 13 случаев × 3 seeds) и 0 в confirm (26 запусков). Evidence
  каждого предложения совпал с независимым oracle и с принятым `HistoryEncoder`. Результат не менялся при
  перестановке строк, колонок и списков.
- Известная допустимая схема стоит на 1-м месте во всех пригодных случаях: audit 27/27, confirm 18/18. Ложных
  отказов 0, правильных отказов 12/12 и 8/8, ложных предложений 0.
- Это не оценка качества на реальных данных. Каталог синтетический и составлен мной, объект там задан конструкцией.
  Предложения остаются гипотезами для INNER-проверки host; выигрыш метрики не измерялся и не заявляется.
- Предел идентичности подтверждён. При одном и том же X (`deceptive_one_object` / `deceptive_two_objects`)
  предложения совпадают во всех 5 seeds. Во втором случае ключ ложно связывает 90 строк на seed, и все 90 были бы
  смешаны при `past_unique_only`. Генератор этого различить не может.
- Нижние предложения (грубые `size+zone`, тройки частей в `long_explicit_key`) дают много ложных совпадений: в audit
  2920 строк по всем предложениям. У top-1 из них только 270, и все в `deceptive_two_objects`. Под `past_unique_only`
  ложно смешались бы 357 строк. Отсеять такие гипотезы должна INNER-проверка host.
- `long_explicit_key` во всех 5 seeds имеет статус `limited` (`check_limit`): явный ключ найден первым, но
  автоматический поиск израсходовал 24 проверки без доказательства полноты, в пуле осталось 2 кандидата.
- Scaling: 100 000 строк обрабатываются за 1.40 с, пик `tracemalloc` 24.3 MiB, 16 проверок, поиск полный.
- После серий код переписан ради скорости. Результат совпал с замороженной версией на 5947 входах, включая счётчики
  и ошибки. Вызов стал быстрее в 2.0–3.1 раза: 100 000 строк за 0.67 с вместо 1.66 с в одном процессе. Подробности —
  «Ускорение после заморозки».

## Интерфейс

```python
from agent.history_schema_proposer import propose_history_schemas

result = propose_history_schemas(
    raw_columns,                              # {column: [str | None, ...]}, только INNER-fit признаки, до preprocessing
    task_type="regression",                   # "classification" -> abstained, другое -> abstained unknown_task_type
    feature_columns=features,                 # признаки без target и технических id; каждая колонка raw_columns
                                              # должна быть среди них
    allowed_period_columns=["t"],             # что host разрешает считать периодом (не больше 2)
    allowed_key_columns=["a", "b", "c", "d"], # что host разрешает как части ключа (не больше 12)
    explicit_key_sets=[["a", "b", "c", "d"]], # явные ключи до 6 частей, проверяются первыми; части из allowed
    numeric_key_columns=["b"],                # только эти части сравниваются как числа
    positive_key_columns=["b"],               # среди числовых: значение <= 0 считается пропуском
    limits=None,                              # переопределение лимитов (только положительные int)
)
```

Результат — конечный JSON-совместимый dict:

```python
    }],

                                         "checked_configs", "unchecked_explicit", "unchecked_pool",

```

Каждый `config` проходит `HistoryConfig.from_json()`, и `to_json()` возвращает его без изменений. В ответе нет
predictions, весов, `accepted` и утверждений об улучшении.

Причины отказа. `abstained`: `classification_task`, `unknown_task_type`, `no_rows`, `no_allowed_period_column`,
`no_allowed_key_columns`, `no_valid_period`, `single_period`, `no_past_coverage`. `limited`:
`period_columns_over_limit`, `key_columns_over_limit`, `explicit_key_width_over_limit`, `row_limit`, `work_limit`,
`check_limit`. При превышении лимитов колонок, строк или работы ни одно значение не читается, первые строки не
берутся. При `check_limit` возвращаются лучшие из проверенных предложений, а счётчики показывают, сколько
кандидатов осталось.

Некорректный вход даёт `ValueError` без значений данных в тексте. Сюда относятся типы, повторяющиеся или
неизвестные имена, колонка `raw_columns` вне `feature_columns`, неровные колонки, значения не `str`/`None` в
используемых колонках, `bool`/`float`/`0` вместо лимита и неизвестный лимит. Входные структуры не изменяются.

## Семантика значений (как у принятого адаптера)

- Период и числовые части ключа: точный `Decimal(text.strip())`. `"61242.0"` равно `"61242"`, `"5E0"` равно
  `"5"`. Ничего не округляется и не проходит через float. Не конечное число считается пропуском. Периоды сравниваются
  только в `sorted()`, без арифметики и без влияния `decimal`-контекста.
- Текстовые части: `text.strip()`, точное сравнение. `None` и пустая строка — пропуск. Буквальные `NA` и `?` —
  обычные значения. Текст `1` и `1.0` в нечисловой колонке различаются.
- Строка с пропуском в любой части ключа или в периоде не имеет истории и не даёт её. Общего объекта у пропусков нет.
- Для строки периода t история есть только в периодах `< t`. Неоднозначность означает, что ключ повторялся внутри
  одного из этих прошлых периодов. Строки того же периода и состав батча историей не считаются.

## Зафиксировано до первого audit

### Лимиты (`DEFAULT_LIMITS`)

| лимит | значение | смысл |
| --- | --- | --- |
| max_period_columns | 2 | разрешённых периодов |
| max_key_columns | 12 | разрешённых частей ключа |
| max_auto_key_width | 3 | ширина автоматического ключа |
| max_explicit_key_width | 6 | ширина явного ключа |
| max_checked_configs | 24 | полных расчётов evidence, явные и автоматические вместе |
| max_proposals | 4 | итоговых предложений |
| max_rows | 250 000 | строк в `raw_columns` |
| max_work | 30 000 000 | план: `rows × (разбираемые колонки + части × периоды + 24 × (ширина + 1))` |

План работы считается до чтения значений по верхней оценке. Если он больше `max_work`, результат `limited` без чтения.

### Поиск

1. Явные ключи со всеми пригодными периодами (не меньше двух различных значений), в порядке (ширина, имена по
   алфавиту). Состав ключа и порядок колонок не меняются.
2. Каждая разрешённая часть ключа один раз просматривается для каждого периода. Считается, сколько строк имеют
   то же значение в более раннем периоде. Это точная верхняя граница покрытия для любого ключа с этой колонкой:
   более широкий ключ покрытие только теряет. Колонки с нулевым покрытием отбрасываются.
3. Автоматические ключи до трёх колонок перебираются best-first. Следующим проверяется кандидат с лучшим
   оптимистичным рангом: граница покрытия считается без неоднозначности. После проверки его расширения на одну
   колонку попадают в пул с границей `min(покрытие ключа, покрытие добавленной колонки)`.
4. Поиск полон, когда ни один непроверенный кандидат уже не может войти в top-4. Иначе он останавливается после
   24 проверок со статусом `limited`, причина `check_limit`. Полнота проверена против полного перебора (тесты).

### Ранжирование

1. Больше `past_unambiguous_history_rows`: строк, которые адаптер смешает при `past_unique_only`.
2. Меньше `past_ambiguous_history_rows`.
3. Меньше колонок ключа.
4. Явный ключ раньше автоматического.
5. Имя периода, затем имена колонок по алфавиту. Это работает только при полном равенстве счётчиков.

Предложение требует хотя бы одной однозначной строки с прошлым. Более широкий ключ, который делит строки так же,
как его подмножество с лучшим рангом, пропускается: его история идентична. Это определяется по тому же периоду,
тем же eligible_rows и тому же числу ключей. Покрытие — структурный показатель, а не доказательство сущности.

### Что считает audit

- Попадание: `(period, множество колонок ключа)` известной схемы есть в top-4. Отдельно считается top-1.
- Ложный отказ: случай `propose`, а предложений нет. Ложное предложение: случай `abstain`, а предложения есть.
- Ложные совпадения по истинным сущностям, для каждого предложения. `false_match_rows` — строки с прошлой историей,
  где среди прошлых строк того же ключа есть другой объект. `false_applied_rows` — то же среди однозначных строк,
  то есть того, что смешает `past_unique_only`.
- Нарушения hard contract: поля и типы, `version`, `scope`, `auto_activate`, `identity_verified`, причина, число
  предложений, `HistoryConfig.from_json` и обратное преобразование, колонки только из разрешённых, политика,
  лимит проверок, JSON без NaN, неизменность входа, запрещённые поля. Сюда же входят evidence против
  независимого oracle (перебор пар строк), evidence против принятого `HistoryEncoder` и повторный вызов с
  перемешанными строками, колонками и списками.
- Предел идентичности: для `deceptive_one_object` и `deceptive_two_objects` предложения должны совпасть, а ложные
  совпадения различаются.

### Ускорение после заморозки (exploratory, 21.10.2026)

После audit и confirm `agent/history_schema_proposer.py` переписан ради скорости. Поиск, ранжирование, лимиты,
форма ответа и сообщения об ошибках не менялись. Серии выше получены на замороженном коде `4aad61ca8e18…`;
текущий код `74677e9ca96c…` проверялся по отдельности, и его прогоны помечены как exploratory.

Что изменено:

- Строки с валидным периодом один раз сортируются по периоду, коды колонок переставляются в этот порядок и
  кешируются. Каждый период превращается в непрерывный срез.
- Evidence считается одним `Counter` на период. Строки новых ключей считаются по росту множества `seen` с поправкой
  на ключи, повторённые внутри периода. Поэлементных проверок по каждой строке больше нет.
- Evidence одиночной колонки, посчитанное при просмотре, переиспользуется её проверкой. В `checked_configs` такая
  проверка по-прежнему учитывается.
- Текст обрезается одним проходом по колонке. Каждое уникальное число и период разбирается один раз.

Доказательство, что результат тот же. Отдельный скрипт вызывает замороженную и новую версию на одних входах и
сравнивает ответ целиком, включая `limits.counts`, или текст ошибки. Замороженная версия берётся как
`git show 5ffe9f9:agent/history_schema_proposer.py`. Скрипт и его вывод лежат локально в игнорируемой
`data/experiments/history_schema/speed_v2_compare/` и в PR не входят: задание разрешает только пять файлов.
Проверялось:

- каталог на 45 seeds (5 серийных и 1–40): каждый случай как есть, с перестановкой строк, колонок и списков и с

## Тесты

`tests/test_history_schema_proposer.py`, 30 тестов:

- контракт: сигнатура, форма ответа для всех статусов, JSON, `auto_activate`/`identity_verified`, конфиги
  проходят `HistoryConfig.from_json`, только стандартная библиотека и нет публичных имён колонок;
- вход: незаконные и неизвестные колонки, колонка вне `feature_columns`, дубликаты, неровные колонки, значения не
  `str`/`None`, неверные лимиты (`bool`, `0`, `-1`, `float`, строка, неизвестный ключ), неизменность входа;
- отказы: classification, неизвестный task_type, нет периода/ключа/строк, один период, нет валидного периода,
  уникальные объекты, повторы только внутри одного периода, только неоднозначное прошлое;
- evidence: история только из более ранних периодов, точность периодов в контексте `prec=3` с ловушками
  `Inexact`/`Rounded`, пропуски и буквальные `NA`/`?`, числовой разбор только для числовых колонок, совпадение
  разбора с `history_keys`, совпадение с oracle и с `HistoryEncoder` на каталоге;
- поиск: полный поиск равен полному перебору на 40 случайных таблицах; без перебора по лимиту результат тот же при
  `max_checked_configs=500`. Ещё проверяются независимость от порядка строк, колонок и списков, предел 24
  проверок со статусом `limited`, приоритет явных ключей с сохранением порядка колонок, пропуск эквивалентных
  расширений, отсутствие чтения значений сверх лимитов и одинаковые предложения при разной скрытой истине.

Мутации кода, которые тесты ловят: утечка истории того же периода, неоднозначность от повторов того же периода,
отключение дедупликации, `auto_activate: true`, `identity_verified: true`, периоды через float, нестрогие пропуски,
игнорирование лимита проверок. Замена `>` на `>=` в условии остановки эквивалентна исходному коду: кортежи рангов
разных кандидатов никогда не равны.

На переписанном коде все 12 мутаций пойманы. Новые из них: повторы первого периода ключа как прошлое, ключ того же
периода в неоднозначности, собственный период как прошлое, пропуск как общий ключ, пустой текст как значение, текст
без `strip`, отключение `positive_key_columns`. В тест на импорты к `collections` и `decimal` добавлены
`itertools` и `operator`. Модули файлов, окружения, сети и часов по-прежнему запрещены.

## Ограничения

- Совпадение наблюдаемого ключа не доказывает один объект. Для одинакового X с разной скрытой идентичностью
  генератор выдаёт одно и то же: `deceptive_*` показывает этот предел. Различить такие случаи может только
  проверка ответов host на INNER, и то лишь косвенно.
- Генератор доверяет разрешению host. Если host разрешит технический счётчик как период, тот будет принят: имя,
  числа и монотонность время не доказывают, решение остаётся за host.
- Ранжирование по покрытию поощряет грубые ключи, когда совпадения разных объектов попадают в разные периоды: такие
  строки не выглядят неоднозначными. Этот риск виден в audit как `false_applied_rows`.
- При равенстве всех счётчиков порядок зависит от имён колонок. В audit и confirm переименованная панель дала тот
  же порядок, но при точном равенстве счётчиков у разных ключей порядок равных может поменяться.
- Лимит 24 проверок часто срабатывает раньше доказательства полноты, если частей ключа много и они сталкиваются
  (`long_explicit_key`; в тестах 15 из 80 случайных таблиц завершились полным поиском). Тогда статус `limited`,
  хотя лучший ключ может быть уже найден.
- Каталог мал и синтетичен: 13 случаев, 40–254 строки. Высокая доля попаданий говорит о корректности механики, а не
  о том, что на неизвестных таблицах ключ-объект найдётся так же.
- Генератор не знает, что произойдёт на строках вне INNER-fit. Ключ, эквивалентный более узкому на этих строках,
  может разойтись с ним на новых данных: такой кандидат не предлагается.
