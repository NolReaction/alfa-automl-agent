## 3. Твоя задача

Исследуй универсальное правило получения классов из вероятностей для
**Macro F1**. Пример семейства правил:

```python
predicted_class = classes[argmax(probabilities * class_multipliers)]
```

Контроль: все множители равны 1, то есть обычный `argmax`.
Кандидат: ограниченные положительные множители, выбранные только на отдельной
внутренней calibration-части или на корректных OOF-предсказаниях.

Причина выбора задачи:

- Публичная классификация оценивается по Macro F1 и содержит редкие классы.
- Предыдущий разбор показал избыточные предсказания некоторых редких классов.
- Простая смена `class_weight` уже исследована и не дала устойчивого выигрыша.
- Множители меняют правило принятия решения и позволяют проверить другой
  механизм без бесконтрольного перебора новых обучений.

Не подгоняй решение под конкретные имена классов, столбцы или датасет.
Не повторяй уже сделанное исследование весов как основную задачу.
Обычная одна температура для всех классов сохраняет `argmax`, поэтому сама
по себе не может улучшить Macro F1; не выдавай её за решение этой задачи.

## 5. Контракт модуля

Модуль должен отделять обучение правила от его применения. Например:

```python
def fit_decision_rule(probabilities, calibration_labels, classes, *, options=None):
    ...

def predict_with_rule(probabilities, prediction_classes, rule):
    ...
```

Можно уточнить интерфейс, если это улучшает корректность. В отчёте перечисли
сигнатуры и приведи один короткий пример использования.

Требования:

- Модуль получает массивы и точные строки классов, не читает файлы или окружение.
- Он получает только разрешённые calibration-ответы, а не outer/audit-ответы.
- Правило сохраняется как конечные JSON-совместимые данные с порядком классов.
- Все множители строго положительны и ограничены заранее заданным диапазоном.
- Есть жёсткий предел числа кандидатов/раундов, детерминированные tie-breaks.
- При равном качестве предпочитай identity или более простое правило.
- Неверная форма, NaN/Inf, несовпадающие классы и недопустимые вероятности
  отклоняются. Порядок вероятностных колонок учитывается явно.
- Метки `01`, `NA`, `class c` сохраняются буквально. `NA` не становится пропуском.
- При слишком малом числе наблюдений, отсутствующем классе или невозможной
  корректной calibration-проверке используй явно описанный identity fallback.
- Правило предназначено для Macro F1. Не меняй им вероятности LogLoss/ROC AUC
  и не подключай его автоматически к задачам с другой метрикой.
- Новых зависимостей, сети и API нет. Код и идентификаторы на английском;
  пояснения и отчёт можно писать по-русски.

## 6. Протокол эксперимента: без утечки ответов

Для каждого заранее заданного случая и seed:

1. Закрепи разбиения и настройки до просмотра внешних оценок.
2. Отдели модельное обучение, calibration и внешнюю проверку.
3. Обучи базовую модель на разрешённой fitting-части; preprocessing также
   обучается только на fitting-части.
4. Получи calibration-вероятности, выбери множители только по calibration.
5. Зафиксируй модель, конфиг и правило.
6. Один раз оцени на внешних ответах identity и выбранное правило.

Контроль и кандидат должны использовать одни базовые вероятности и одни
внешние строки. Тогда сравнивается именно правило, а не одновременно другая
модель, другой split и другое число деревьев.

OOF-подход допустим, если не нарушает границы. При refit базовой модели после
calibration явно опиши изменение распределения вероятностей и одинаковый
refit контроля/кандидата. Внешние ответы не возвращаются в настройку правила.

Используй существующие политики групп и времени там, где они применимы:
одинаковые исходные признаки не должны попадать в обе стороны split; время
должно двигаться вперёд. Невозможный split не заменяй более выгодным random.
Если для безопасного выбора политики нужен контекст будущего host, опиши
этот аргумент интерфейса и ограничение, а не угадывай его по ответам.

Не используй outer/audit для выбора числа раундов, диапазона множителей,
минимальной поддержки класса, seed или лучшей версии алгоритма. Если после
просмотра audit меняешь метод, отметь результаты как exploratory; новая
проверка должна использовать ещё не просмотренные данные.

## 11. Критерии готовности и ответ первому GPT

Работа завершена, когда есть:

- небольшой изолированный модуль с ясным интерфейсом;
- воспроизводимый ограниченный эксперимент и корректный контроль;
- содержательные тесты alignment/identity/редких классов/некорректных входов;
- результаты всех заранее заданных случаев, включая ухудшения и fallback;
- отчёт с точными командами и ограничениями;
- отдельный commit/ветка/PR, без интеграции в основной runtime.

В финальном сообщении Диме и первому GPT напиши:

1. Ссылка на ветку/PR и точный commit SHA.
2. Какие файлы созданы.
3. Что изменяет правило и какие данные оно использует.
4. Таблица control/candidate по всем проверкам и число побед/ничьих/поражений.
5. Какие тесты запускались и что прошло.
6. Ограничения, отрицательные результаты и непроверенные части.
7. Точные точки будущей интеграции, если результаты её оправдывают.

Не заканчивай только предложением плана или обещанием продолжить.
Не меняй стандартные настройки ради красивого локального результата.
